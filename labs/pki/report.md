# Отчёт о стенде Web → Order

Прогон 15 ноября 2026 года. Windows, Linux-движок Docker Desktop, Docker Compose **v5.7.0**. Тестовый проект `ceilings-pki-be34e209`. Фактические версии: Envoy **1.40.1** (BoringSSL), `step-ca` **0.30.2**, `step` **0.31.0**. Все четыре проверки прошли. [Как повторить прогон](README.md) · [Результаты и серийные номера в JSON](acceptance.json).

| Проверка | Фактический результат |
|---|---|
| 1. Первая выдача и mTLS | **Прошла.** Запрос через оба Envoy дал HTTP 200. Отсутствующий клиентский сертификат и неправильный SAN клиента отклонены. Сертификат сервера с неправильным SAN проходил проверку под собственным именем, а Web при запросе к Order получал отказ. Посторонний контейнер видел mTLS-вход Order, а сокеты и прямые HTTP-входы были недоступны. |
| 2. Плановое обновление | **Прошла.** После прерванной записи проходил прежний комплект Web. После `rekey` на новых рукопожатиях изменились серийные номера и отпечатки открытых ключей Web и Order. Время запуска обоих Envoy осталось прежним. |
| 3. Аварийный отзыв | **Прошла в обоих направлениях.** Остановка проверяющего Envoy оборвала открытый ответ. После применения свежего CRL Order отклонил ещё действующий сертификат Web с TLS-ошибкой `certificate revoked`. При предъявлении ещё действующего отозванного сертификата Order Envoy Web вернул HTTP 503. С новыми сертификатами вызов проходил. |
| 4. Недоступность CA и истечение CRL | **Прошла отдельно для каждого списка.** При выключенном CA запрос давал HTTP 200 по действующей локальной копии. После её `nextUpdate` запрос давал HTTP 503 при двух действующих сертификатах и действующем втором списке. Загрузка свежей копии вернула HTTP 200. |

Итоговый прогон подтвердил ожидаемое поведение всех четырёх проверок. При отладке файловому SDS потребовались `node.id`, `node.cluster` и права чтения сертификата для непривилегированного Envoy. Для операторского отзыва сценарий использует отдельно подписанный токен. После этих исправлений проверки повторены на чистом проекте. Тестовые контейнеры и тома с ключами удалены.

На стенде запросы обновления запускает сценарий через отдельные контейнеры Web и Order. Он проверяет загрузку файлов, но рабочие расписания, оповещения и хранение корневого ключа на отдельном физическом носителе проверяются отдельно.

Для следующего обсуждения остаются сертификат, полученный через `rekey` до обнаружения утечки, сохранение отзывов после восстановления CA из старой копии и прекращение доверия к прежнему промежуточному CA при обновлении. Защита Web → Auth и соединений с PostgreSQL и RabbitMQ остаётся отдельной задачей проектирования.
