# Стенд mTLS Web → Order

Эксперимент на этапе проектирования Ceilings. Маршрут запроса проходит от тестового клиента через Unix-сокет в Envoy Web, по mTLS в Envoy Order и по второму Unix-сокету до HTTP-обработчика. Обработчик возвращает `order ok`. Compose создаёт отдельные тома и две внутренние сети. HTTP, CA и порты Envoy доступны только внутри стенда.

В [compose.yaml](compose.yaml) закреплены Envoy **1.40.1** и `step-ca` **0.30.2**. В [Dockerfile](Dockerfile) закреплён `step` **0.31.0**. Источники версий: [Envoy](https://github.com/envoyproxy/envoy/releases/tag/v1.40.1), [step-ca](https://github.com/smallstep/certificates/releases/tag/v0.30.2), [step](https://github.com/smallstep/cli/releases/tag/v0.31.0).

Для прогона нужны Python 3.11+, Docker Compose и доступный Linux-движок Docker. Первый запуск загрузит образы и соберёт образ инструментов. Из корня Ceilings:

```powershell
docker info --format '{{.OSType}}'
docker compose version
python labs/pki/run.py --report labs/pki/acceptance.json
```

При установке Docker Desktop для текущего пользователя скрипт пробует найти `docker.exe` в каталоге установки. Для другого расположения передайте абсолютный путь аргументом `--docker`. Скрипт создаёт проект с уникальным именем и в конце удаляет его контейнеры, сети и тома. Ключи и токены генерируются для этого проекта. JSON содержит измерения, серийные номера и отпечатки открытых ключей.

Сокращённые сроки стенда: сертификаты на 30 минут, сервисный CRL на 150 секунд, плановый выпуск CRL через 40 секунд. Для проверки истечения корневого списка подписывается отдельный список на 30 секунд. Обновление и получение CRL запускает сценарий приёмки через отдельные контейнеры Web и Order. Он проверяет механизмы, а рабочее расписание с часовыми порогами остаётся частью технического дизайна.

## Что проверяет прогон

| Проверка | Наблюдаемый результат |
|---|---|
| Первая выдача и доступ | Оператор подписывает одноразовое разрешение, привязанное к CSR и имени. Запрос приходит через оба Envoy. Отдельные прогоны отклоняют отсутствующий клиентский сертификат и неверные SAN клиента и сервера. Контейнер в той же сети видит mTLS-вход Order, но прямой HTTP-вход и сокеты ему недоступны. |
| Плановое обновление | Из нового рукопожатия получаем серийный номер и отпечаток открытого ключа. При прерывании записи до замены `tls-sds.yaml` проходит прежний комплект. При успешном переключении наблюдаем новые сертификат и ключ, а время старта обоих Envoy остаётся прежним. |
| Аварийный отзыв | Для Web и Order по очереди открываем долгий HTTP-ответ, останавливаем проверяющий прокси и фиксируем обрыв. После запуска со свежим CRL проверяем новый сертификат и отказ по старому, пока старый ещё действует. |
| CA и сроки CRL | По отдельности дожидаемся истечения сервисного и корневого списков. До истечения локальной копии запрос проходит при выключенном CA. После истечения новый TLS-вызов отклоняется, хотя сертификаты действительны. После загрузки свежего списка вызов проходит снова. |

Скрипт завершает прогон на первой ошибке и отмечает последующие проверки как невыполненные. Чтобы сохранить проект для диагностики, добавьте `--keep`. Из каталога `labs/pki` можно посмотреть его состояние и удалить его вручную:

```powershell
docker compose -p <имя-из-вывода> ps -a
docker compose -p <имя-из-вывода> logs ca envoy-web envoy-order
docker compose -p <имя-из-вывода> --profile tools down --volumes --remove-orphans
```

Удаление томов уничтожает тестовый CA и ключи этого проекта. Фактический прогон и его ограничения описаны в [отчёте](report.md).
