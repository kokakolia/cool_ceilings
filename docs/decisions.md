# Журнал решений Ceilings

Актуально на 24 ноября 2026 года.

Здесь сохраняем существенные вопросы, рассмотренные варианты, причины выбора и принятые компромиссы. Это помогает автору восстановить ход рассуждений и объяснить устройство проекта. Учебная цель — самостоятельная причина выбора, её отмечаем явно.

Актуальные правила и устройство системы описаны в [продукте](product.md), [сценариях](use-cases.md) и [техническом дизайне](first-scenario-design.md). Журнал объясняет причины этих решений. Предложения и открытые детали не становятся требованиями только из-за упоминания здесь.

При пересмотре сохраняем прежнюю запись, помечаем её как заменённую и добавляем ссылку на новое решение. Не восстанавливаем по догадкам даты, альтернативы или аргументы. Первые две записи составлены ретроспективно по обсуждению с автором и действующим документам.

## 001. Разделение приложения на микросервисы

**Статус:** принято на этапе проектирования.

**Дата записи:** 14 ноября 2026 года. Точная дата исходного решения не восстановлена.

### Какой вопрос решали

Выбирали устройство учебного проекта до реализации. Автор хотел освоить FastAPI, SQLAlchemy, PostgreSQL, Docker, микросервисный и событийный подходы с брокером сообщений. Обсуждали, насколько дробить приложение и оправдана ли сложность распределённой системы при небольшом продукте.

Речь о разделении ответственности при проектировании, а не о миграции уже работающего монолита.

### Рассмотренные варианты

- Единое приложение — исходная альтернатива микросервисному устройству. Подробное сравнение вариантов внутреннего устройства монолита в этой записи не восстановлено.
- Два сервиса с большей частью логики в основном приложении. Автор счёл такое разделение недостаточным для своей учебной цели и предложил выделить заказы отдельно.
- Четыре сервиса с отдельными обязанностями и владельцами данных — выбранный состав.

### Что выбрали

| Сервис | Ответственность |
|---|---|
| Web API / веб-приложение | Кабинет и панель администратора, организация обращений к внутренним сервисам. Собственной БД нет |
| `AuthService` | Учётные записи, подтверждённый email, вход, роли и сессии |
| `OrderService` | Заказы, контакты в заказе, доступ к конкретному заказу, его жизненный цикл и история. Позже — замеры, сметы и визиты |
| `NotiService` | Доставка писем и обработка заданий на отправку |

У трёх сервисов с постоянными данными — собственные экземпляры PostgreSQL. Сервис владеет своими данными, другие сервисы обращаются через его интерфейс. Для обмена предусмотрены синхронные вызовы и сообщения через RabbitMQ. Контейнеризация входит в учебную цель.

Будущий файловый сервис для фотографий и S3-совместимого хранилища держим в плане вместе с отзывами. Он не входит в текущие четыре сервиса и не требуется для первого выпуска.

### Почему выбрали

Главная причина — желание автора получить практический опыт распределённой системы: границы ответственности, взаимодействие сервисов, независимое хранение данных, доставка событий и работа со сбоями. Автор явно принял дополнительную сложность как часть обучения и не хотел исключать её только потому, что проект учебный.

Решение не основано на доказанной нехватке производительности монолита. Четыре сервиса дают конкретные области ответственности, дальнейшее дробление требует отдельного обсуждения.

### Последствия и ограничения

- Появляются сетевые ошибки, частичная недоступность, повторная доставка сообщений и необходимость согласовывать контракты.
- Данные разных сервисов нельзя считать частью одной обычной транзакции PostgreSQL. Сохранность изменений и доставку событий нужно проектировать явно.
- Усложняются запуск окружения, диагностика и проверки взаимодействия сервисов.
- Количество сервисов само по себе не доказывает качество архитектуры или готовность к высокой нагрузке.

**Связанный документ:** [технический дизайн первого сценария](first-scenario-design.md).

## 002. JWT access tokens вместе с серверными сессиями

**Статус:** принято. Сроки сессий закреплены в [решении 023](#023-сроки-сессий-и-ротация-refresh-токенов), действующая политика ротации — в [решении 030](#030-строгая-ротация-refresh-токенов).

**Дата записи:** 14 ноября 2026 года. Запись объединяет несколько последовательных обсуждений, их точные даты не восстановлены.

### Какой вопрос решали

Первоначальный подход предполагал непрозрачный идентификатор сессии в cookie и обращение Web API в `AuthService` при каждом защищённом запросе. Автор поставил вопрос о дополнительной нагрузке и зависимости от доступности Auth при росте числа пользователей.

Нужно было совместить локальную проверку обычных запросов с управлением сессиями и актуальными правами. Для администратора уже было согласовано, что отзыв прав должен блокировать следующий защищённый запрос, включая чтение.

### Рассмотренные варианты

- Серверная сессия с актуальной проверкой через `AuthService` на каждый защищённый запрос. Отказались от такой обязательной проверки для обычного клиентского чтения.
- JWT для клиентов и только серверные сессии для администраторов. Автор предложил этот промежуточный вариант, затем выбрал общую схему токенов и сессий для обеих категорий.
- Короткоживущий JWT, rotating refresh token и серверная сессия для каждого пользователя, с дополнительной актуальной проверкой там, где она нужна — выбранный подход.

### Что выбрали

- `AuthService` управляет серверными сессиями, выдаёт короткоживущие JWT access tokens и refresh tokens с ротацией для клиентов и администраторов.
- Web API локально проверяет JWT, включая подпись, срок, издателя и получателя.
- Обычное клиентское чтение не требует вызова `AuthService` на каждый запрос.
- Для критических операций дополнительно проверяются актуальная сессия и права через `AuthService`. В первом сценарии такая проверка нужна при подаче заявки.
- Для каждого защищённого административного запроса, включая чтение, обязательна актуальная проверка через `AuthService`. Если она недоступна или неуспешна, запрос не разрешается.
- Обновление токенов не продлевает абсолютный срок серверной сессии.

Локально проверенный JWT содержит сведения на момент выдачи. Он не доказывает, что сессия ещё не отозвана или права не изменились. На критическом пути нужны обе успешные проверки, поэтому формулировка «JWT запрещает, сессия разрешает» не описывает выбранную схему достаточно точно.

### Почему выбрали

Обычное клиентское чтение получает меньшую зависимость от `AuthService` и не создаёт там дополнительный запрос на каждое чтение. Серверные сессии сохраняют управление обновлением токенов и отзывом доступа, а актуальные проверки защищают операции, для которых нельзя полагаться только на сведения из ранее выданного JWT.

Это компромисс по свежести прав, доступности и сложности. Мы не установили, что первоначальная схема не выдержала бы тысячи пользователей: измерений ещё нет.

### Связанная дискуссия о доступе к заказам

Автор предложил сохранять разрешённый активный заказ в JWT, чтобы облегчить чтение в `OrderService`. Обсуждался также кеш. Эти предложения не приняли в работу.

Выяснили, что проверку владельца можно объединить с самим чтением:

```sql
WHERE id = :order_id AND owner_id = :authenticated_user_id
```

Идентификатор пользователя поступает из доверенного серверного контекста. При чтении по первичному ключу индекс позволяет найти заказ без перебора всех заказов. Отдельного сетевого запроса «может ли пользователь читать заказ» не требуется. Проверка принадлежности остаётся в `OrderService`, идентификатор активного заказа и разрешения на заказы в JWT не добавляем.

Автор принял этот подход после объяснения стоимости проверки. Redis ради обхода `OrderService` или проверки владельца не вводим. Решения о дальнейшей оптимизации принимаем по измерениям.

### Последствия

Недоступность `AuthService` блокирует обновление токенов и операции с обязательной актуальной проверкой. Обычное клиентское чтение с действительным JWT сохраняется при доступности остального пути запроса.

**Связанные документы:** [технический дизайн первого сценария](first-scenario-design.md), [сценарии и критерии приёмки](use-cases.md).

## 003. mTLS через Envoy для удостоверения вызывающего сервиса

**Статус:** принято на этапе проектирования.

**Дата записи:** 14 ноября 2026 года. Точная дата исходного решения не восстановлена.

**Источник:** автор восстановил обсуждение с агентом-исполнителем. Технические уточнения аргументов приведены отдельно от исходной мотивации.

### Какой вопрос решали

Как `OrderService` убеждается, что запрос с контекстом пользователя пришёл от доверенного веб-приложения. Это отдельная задача от проверки пользовательского JWT и права пользователя читать или менять заказ.

### Рассмотренные варианты

| Вариант | Что обсуждали и почему не выбрали или выбрали |
|---|---|
| API key | Автора не устроили передача общего секрета с каждым запросом и необходимость организовать его проверку, привязку к вызывающей стороне, отзыв и замену. Не хотели самостоятельно строить управление сервисными ключами и разрешениями вокруг этого механизма |
| OAuth 2.0 Client Credentials | Рассматривали как серьёзную альтернативу. Для текущего взаимодействия не понадобился отдельный механизм выпуска сервисных access tokens и разграничения доступа через них. Подход остаётся применимым при иных требованиях |
| mTLS | Выбрали взаимное удостоверение сторон на уровне TLS. Основная мотивация автора — соответствие задаче аутентификации сервисов и преимущество перед обычным Bearer-токеном: предъявления скопированного сертификата недостаточно без владения закрытым ключом |

### Что выбрали

Для соединений веб-приложения с `OrderService` используем mTLS через Envoy. Выбор не распространяется автоматически на все остальные соединения системы.

- Envoy требует клиентский сертификат, проверяет цепочку до доверенного CA и точное имя веб-приложения в SAN. Сертификата произвольного сервиса от того же CA недостаточно.
- Веб-приложение проверяет сертификат серверной стороны, включая доверие к CA и ожидаемое имя.
- Envoy передаёт принятые запросы в FastAPI через локальный Unix-сокет. Прямого сетевого входа в FastAPI в обход проверки нет.
- `OrderService` отдельно проверяет пользовательские права и принадлежность заказа. Успешное mTLS-соединение не даёт пользователю права на произвольный заказ.

Envoy выбрали как прокси для обработки межсервисного трафика (data plane) с поддержкой mTLS: клиентских сертификатов, проверки цепочки доверия и имени стороны. В этой схеме он является инфраструктурным компонентом `OrderService`.

### Уточнения исходных аргументов

- API key не является ненадёжным сам по себе. HTTPS защищает его при передаче. Причина отказа относится к управлению общим секретом и последствиям его утечки, а не к неизбежной передаче открытым текстом.
- В проекте есть роли клиента и администратора. Отсутствие потребности в отдельной системе сервисных ролей для этого соединения не означает отсутствия авторизации. Ограничение допуска конкретным SAN также задаёт политику доступа.
- OAuth Client Credentials применим и без сложной системы ролей. Выбор mTLS означает, что для текущей задачи не вводим отдельный выпуск сервисных OAuth-токенов. OAuth и mTLS могут использоваться совместно.
- Сертификат не является секретом. mTLS требует доказательства владения закрытым ключом, который не передаётся другой стороне при соединении. Обычный Bearer-токен позволяет действовать тому, кто им завладел. Это конкретное преимущество mTLS, но не безусловная гарантия большей безопасности: закрытый ключ также можно скомпрометировать. OAuth допускает привязку токенов к сертификату.

### Последствия и открытые детали

- Вместо управления API keys появляются управление CA, выпуск, доставка, ротация сертификатов и защита закрытых ключей. Эта работа не исчезает благодаря выбору mTLS.
- На момент исходного обсуждения для разработки был предложен локальный CA. Позже выбран `step-ca` — см. решение 004 ниже. Закрытые ключи передаются как секреты вне репозитория.
- Нужно проверять отказ без сертификата, с недоверенным сертификатом и с сертификатом другого сервиса от того же CA, а также невозможность обхода Envoy.

**Связанный документ:** [технический дизайн первого сценария](first-scenario-design.md).

**Источники технических уточнений:** [OAuth 2.0 Client Credentials, RFC 6749](https://www.rfc-editor.org/rfc/rfc6749#section-4.4), [mTLS и привязка OAuth-токенов к сертификатам, RFC 8705](https://www.rfc-editor.org/rfc/rfc8705), [поддержка TLS в Envoy](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/security/ssl).

## 004. step-ca для внутренних сертификатов учебного окружения

**Статус:** принято на этапе проектирования.

**Дата записи:** 14 ноября 2026 года.

### Какой вопрос решали

После выбора mTLS через Envoy потребовалось определить, кто выдаёт сертификаты сервисам и как организовать их жизненный цикл. Envoy проверяет сертификаты и использует ключи, но сам не организует выдачу, обновление и прекращение доверия.

Автор хотел понимать основания выбора между `step-ca`, SPIRE и Vault PKI. Разработка собственного CA не является обязательной учебной целью.

### Что выбрали и почему

Используем `step-ca` как внутренний CA учебного окружения. Это инфраструктурный компонент; состав четырёх прикладных сервисов Ceilings не меняется.

Главная причина — соответствие текущей задаче: выдача и обновление сертификатов для небольшого, заранее известного набора сервисов в Docker Compose. `step-ca` специализируется на сертификатах и поддерживает автоматизированную выдачу и обновление. Это позволяет отдельно изучить разрешение на выпуск, доверие, обновление и применение сертификата в Envoy.

Автоматическое удостоверение запущенных процессов и общая платформа управления всеми секретами не выбраны задачами текущего этапа. Поэтому дополнительные возможности SPIRE и Vault пока не определяют выбор. Это оценка соответствия объёму проекта, а не доказанное превосходство `step-ca` по безопасности, скорости или расходу ресурсов. Сравнительных испытаний не проводили.

### Рассмотренные альтернативы

| Вариант | Почему не выбрали сейчас; когда стоит вернуться |
|---|---|
| Выпуск служебным скриптом через OpenSSL или Python `cryptography` | Подходил для ручного выпуска нескольких сертификатов и первоначально предлагался исполнителем. Автор выбрал готовый CA с возможностью автоматизации выдачи и обновления. Скрипты настройки и интеграции по-прежнему могут понадобиться |
| Собственный CA на FastAPI | Потребовал бы самостоятельно реализовать проверку права на имя, ограничения выдачи, учёт, обновление, отзыв и восстановление. Автор подтвердил, что разработка CA необязательна; отдельную реализацию не вводим |
| SPIRE | Решает также удостоверение узлов и процессов по заданным признакам, использует Server и агенты, умеет динамически передавать удостоверения в Envoy через SDS. Вернуться при цели автоматической идентификации контейнеров и управления их удостоверениями. Небольшой размер проекта сам по себе не исключает SPIRE |
| Vault PKI | Выдаёт сертификаты через механизмы аутентификации и политик Vault. Особенно уместен, если Vault уже используется или нужен единый подход к сертификатам, паролям БД и другим секретам. Такая платформа пока не выбрана |
| cert-manager | Обсуждался как автоматизация управления сертификатами в Kubernetes, в том числе через внешние CA. Для текущего Docker Compose не выбираем; это не прямая замена CA во всех конфигурациях |

### Последствия и границы решения

- `step-ca` добавляет к окружению отдельный инфраструктурный компонент со своими ключами и состоянием.
- `step-ca` выдаёт сертификаты. Получение и применение новых сертификатов в Envoy требуют интеграции.
- Область решения — внутренние сертификаты для согласованных соединений mTLS. Публичный HTTPS, сертификат внешнего SMTP и ключи подписи JWT управляются отдельно.

**Связанные документы:** [дизайн первого сценария](first-scenario-design.md), [план разработки](development-plan.md).

**Источники технических возможностей:** [step-ca](https://smallstep.com/docs/step-ca/), [устройство SPIRE](https://spiffe.io/docs/latest/spire-about/spire-concepts/), [SPIRE и Envoy SDS](https://spiffe.io/docs/latest/microservices/envoy-x509/readme/), [Vault PKI](https://developer.hashicorp.com/vault/docs/secrets/pki), [cert-manager](https://cert-manager.io/docs/), [создание сертификатов с cryptography](https://cryptography.io/en/latest/x509/tutorial/).

## 005. Первоначальная выдача сертификатов по разрешению оператора

**Статус:** принято на этапе проектирования.

**Дата записи:** 15 ноября 2026 года.

Нужно было определить, кто подтверждает право Envoy получить сертификат с именем сервиса при первом запуске окружения. Например, чтобы Envoy Order мог доверять имени Web, кто-то должен сначала разрешить его выдачу.

Первую выдачу разрешает оператор развёртывания. Служебная команда создаёт ключ и запрос на сертификат для конкретного Envoy. Оператор выдаёт через JWK provisioner короткоживущий одноразовый токен на конкретное имя в SAN и на этот запрос. Команда передаёт запрос и токен в `step-ca` по соединению с заранее установленным доверием к CA. Закрытый ключ остаётся на стороне Envoy.

В Compose набор сервисов заранее известен оператору. Он связывает имя с конкретным запросом, а `step-ca` проверяет эту связь при выдаче. Поэтому один токен нельзя использовать для выпуска сертификата на другое имя или для другого запроса с тем же именем. Для нового окружения требуется действие оператора.

**Связанный документ:** [технический дизайн первого сценария](first-scenario-design.md#первоначальная-выдача).

**Источник:** [токены выдачи Smallstep](https://smallstep.com/docs/step-cli/reference/ca/token/).

## 006. Срок сервисных сертификатов и начало обновления

**Статус:** принято на этапе проектирования.

**Дата записи:** 15 ноября 2026 года.

В учебном окружении сертификаты Envoy действуют 24 часа. В режиме выпуска первую автоматическую попытку назначаем за 8 часов до истечения. Запас даёт время повторить обновление при временной недоступности `step-ca`. На этапе 2 запуск ручной по [решению 022](#022-обслуживание-сертификатов-и-crl-по-этапам).

**Связанный документ:** [технический дизайн первого сценария](first-scenario-design.md#срок-сервисных-сертификатов-и-начало-обновления).

## 007. Плановое обновление сертификатов Envoy через файловый SDS

**Статус:** принято на этапе проектирования.

Обсудили обычный перезапуск прокси после замены файлов и загрузку обновления в работающий Envoy. Выбрали файловый SDS. Процесс обновления получает сертификат у `step-ca`, а Envoy подхватывает подготовленный комплект с диска и применяет его для новых TLS-соединений.

Перезапуск с одним экземпляром прокси на сервис прерывает открытые соединения и на время останавливает вызовы через этот прокси. При регулярном обновлении короткоживущих сертификатов файловый SDS устраняет регулярную паузу. Этот вариант требует настроить файловый источник и согласованную публикацию сертификата и ключа.

**Связанный документ:** [технический дизайн первого сценария](first-scenario-design.md#применение-обновлённого-сертификата-в-envoy).

**Источник:** [файловое обновление сертификатов в Envoy](https://www.envoyproxy.io/docs/envoy/latest/configuration/security/secret#key-rotation).

## 008. Отдельный процесс обновления для каждого Envoy

**Статус:** принято на этапе проектирования.

Для Envoy Web и Envoy Order запускаем по одному процессу обновления в отдельных контейнерах из одного образа. Каждый использует сертификат и закрытый ключ своего прокси, чтобы обновить сертификат через `step-ca`, и публикует файлы для SDS этого Envoy.

Общий процесс потребовал бы доступа к обоим закрытым ключам. Два экземпляра позволяют ограничить доступ каждого процесса одним ключом и обновлять сертификаты независимо.

**Связанный документ:** [технический дизайн первого сценария](first-scenario-design.md#процессы-обновления-сертификатов).

## 009. Хранение ключей и восстановление CA

**Статус:** принято на этапе проектирования.

У каждой пары Envoy и процесса обновления свой постоянный каталог с файлами вне репозитория. Envoy читает файлы, а процесс обновления может их заменять. При потере сервисного ключа выпускаем новую пару и сертификат под тем же доверенным корнем.

Корневой закрытый ключ хранится отдельно от запущенного окружения. Для восстановления рабочего `step-ca` сохраняем зашифрованную копию промежуточного ключа, цепочки CA, конфигурации и состояния базы. Это позволяет восстановить и подпись под прежним корнем, и правила выдачи, и сведения об отзывах и использованных токенах на момент копии. Архив храним на внешнем диске, который отключаем после копирования. Пароль к архиву хранится отдельно.

**Связанный документ:** [технический дизайн первого сценария](first-scenario-design.md#хранение-и-восстановление-ключей-и-ca).

## 010. Имена Web и Order в сервисных сертификатах

**Статус:** принято на этапе проектирования.

Для учебного окружения выбраны DNS SAN `web.ceilings.test` для Envoy Web и `order.ceilings.test` для Envoy Order. Envoy Order требует точное имя Web в клиентском сертификате. Envoy Web требует точное имя Order в серверном сертификате. Оба прокси проверяют цепочку до доверенного CA.

Точное имя позволяет допустить нужный сервис среди всех сертификатов, выпущенных этим CA. Зона `.test` зарезервирована для тестовых окружений.

**Связанный документ:** [технический дизайн первого сценария](first-scenario-design.md#проверка-вызывающего-сервиса).

## 011. Назначение сертификатов Web и Order

**Статус:** принято на этапе проектирования.

Используем один внутренний сертификат на Envoy. Сертификат Web имеет `clientAuth` для вызова Order и обновления в `step-ca`. Сертификат Order имеет `serverAuth` для приёма соединения от Web и `clientAuth` для обращения процесса обновления к CA.

Сертификат Order только с `serverAuth` потребовал бы отдельного способа обновления. Выбрали единый порядок для обоих прокси: процесс обновления удостоверяет себя в `step-ca` действующим сертификатом и ключом своего Envoy. Допуск на API Order по-прежнему требует точного имени Web.

**Связанный документ:** [технический дизайн первого сценария](first-scenario-design.md#назначение-сервисных-сертификатов).

**Источник:** [обновление сертификатов в Smallstep](https://smallstep.com/docs/step-ca/basic-certificate-authority-operations/#renew-a-certificate).

## 012. Сбой обновления и истечение сервисного сертификата

**Статус:** принято на этапе проектирования.

Действующий сертификат сохраняет доступ во время временного сбоя CA. В режиме выпуска процесс пишет причину в журнал и повторяет запрос каждые 5 минут до истечения текущего сертификата. Если до истечения остался час, а обновление ещё не удалось, процесс предупреждает оператора. Если CA восстановился вовремя, очередная попытка завершает обновление автоматически. На этапе 2 команду повторяет оператор по [решению 022](#022-обслуживание-сертификатов-и-crl-по-этапам).

После истечения требуется новая выдача с одноразовым разрешением оператора. Просроченный сертификат отклоняется при новых TLS-рукопожатиях. Так короткие сбои обрабатываются автоматически, а восстановление после истечения использует согласованную процедуру первой выдачи.

**Связанный документ:** [технический дизайн первого сценария](first-scenario-design.md#недоступность-ca-и-истечение-сертификата).

## 013. Активный отзыв сервисных сертификатов

**Статус:** принято на этапе проектирования.

При утечке ключа Envoy оператор отзывает все его ещё действующие сертификаты в `step-ca` и применяет подписанный список отозванных сертификатов (CRL) у проверяющего Envoy. Уже открытые соединения закрываются отдельным действием. Доступ восстанавливается после первой выдачи с новым ключом.

Рассмотрели пассивный отзыв. Он блокирует обновление в CA, но оставляет до 24 часов, в течение которых Envoy может принимать действующий сертификат. Выбрали активный отзыв, чтобы проверяющий прокси прекращал принимать сертификат сразу после загрузки списка. Локальная копия CRL позволяет проверять отзыв без обращения в CA на каждом соединении.

**Связанный документ:** [технический дизайн первого сценария](first-scenario-design.md#отзыв-сервисного-сертификата-при-утечке-ключа).

**Источники:** [отзыв в Smallstep](https://smallstep.com/docs/step-ca/revocation/), [проверка CRL в Envoy](https://www.envoyproxy.io/docs/envoy/latest/api-v3/extensions/transport_sockets/tls/v3/common.proto.html).

## 014. Восстановление доверия после компрометации CA

**Статус:** принято на этапе проектирования.

При утечке промежуточного ключа сохраняем защищённый корень. Корень подписывает новый промежуточный сертификат и список отзыва старого промежуточного сертификата. Проверяющие стороны прекращают принимать всю старую цепочку, включая запросы обновления. Для сервисов повторяем первую выдачу под новым промежуточным CA.

При утечке корневого ключа создаём новый корневой и промежуточный CA, доставляем новый корень доверенным способом, удаляем старый корневой сертификат из доверия и заново выдаём сервисные сертификаты. Допускаем простой на время переключения и закрытия прежних TLS-сессий.

В первом случае корень ещё может удостоверить нового подписанта и подтвердить отзыв прежнего. Во втором само доверие к корневой подписи потеряно, поэтому требуется новый корень у всех участников этого контура.

**Связанный документ:** [технический дизайн первого сценария](first-scenario-design.md#восстановление-после-компрометации-ca).

## 015. Новый ключ Envoy при каждом плановом обновлении

**Статус:** принято на этапе проектирования.

Для Web и Order используем `step ca rekey` при каждом плановом обновлении. Процесс получает сертификат для нового ключа и публикует оба файла одним комплектом для SDS. При ошибке сохраняется предыдущий действующий комплект.

Обычное `renew` сохраняло бы прежний ключ. Выбрали `rekey`, чтобы менять ключ по тому же графику, что и сертификат. Плановая смена ключа и активный отзыв при утечке остаются отдельными процедурами.

**Связанный документ:** [технический дизайн первого сценария](first-scenario-design.md#процессы-обновления-сертификатов).

**Источник:** [команда step ca rekey](https://smallstep.com/docs/step-cli/reference/ca/rekey/).

## 016. Плановая замена ключей CA

**Статус:** принято на этапе проектирования.

Промежуточный сертификат действует 1 год, корневой — 5 лет. Оператор начинает замену каждого ключа за 30 дней до истечения соответствующего сертификата. Запас даёт время проверить переход и закончить его до истечения сертификата.

При плановой замене промежуточного CA сохраняем корень и переводим сервисы на новую цепочку при штатном обновлении. При плановой замене корневого CA сначала добавляем новый корень в доверенные, затем переключаем выдачу и после перехода удаляем прежний корень. Временное доверие обоим корням даёт участникам время перейти на новую цепочку.

**Связанный документ:** [технический дизайн первого сценария](first-scenario-design.md#плановая-замена-ключей-ca).

**Источник:** [замена сертификатов CA в Smallstep](https://smallstep.com/docs/step-ca/certificate-authority-server-production/#rotating-ca-certificates).

## 017. Доставка списков отзыва в Envoy

**Статус:** принято на этапе проектирования.

При отзыве сервисного сертификата `step-ca` формирует обновлённый подписанный CRL. Существующие процессы обновления Web и Order получают список, проверяют подпись и срок, затем публикуют его для файлового SDS. Envoy проверяют списки локально, поэтому каждое TLS-соединение может проверяться без обращения к CA.

Для аварийного отзыва предусмотрена принудительная загрузка оператором с проверкой, что Envoy отклоняет отозванный сертификат. Список, подписанный корневым ключом для отзыва промежуточного CA, оператор доставляет через доверенный канал развёртывания.

**Связанный документ:** [технический дизайн первого сценария](first-scenario-design.md#доставка-списков-отзыва-в-envoy).

**Источники:** [настройки CRL в Smallstep](https://smallstep.com/docs/step-ca/configuration/), [проверка CRL в Envoy](https://www.envoyproxy.io/docs/envoy/latest/api-v3/extensions/transport_sockets/tls/v3/common.proto.html).

## 018. Срок сервисного CRL и поведение при истечении

**Статус:** принято на этапе проектирования.

Сервисный CRL действует 24 часа. `step-ca` перевыпускает его каждые 8 часов и при отзыве. При сбое загрузки используется действующая локальная копия до `nextUpdate`. В режиме выпуска процессы проверяют список раз в минуту, журналируют сбои и предупреждают оператора за час до истечения, если свежей копии ещё нет. На этапе 2 загрузку запускает оператор по [решению 022](#022-обслуживание-сертификатов-и-crl-по-этапам).

После истечения списка отклоняем новые mTLS-соединения до применения действующего CRL. Это сохраняет работу при кратком сбое CA и ограничивает время, в течение которого Envoy полагается на прежние сведения об отзывах. Прекращение уже открытых соединений при известном отзыве выполняется отдельно.

**Связанный документ:** [технический дизайн первого сценария](first-scenario-design.md#срок-и-обновление-сервисного-crl).

## 019. Срок корневого CRL и поведение при истечении

**Статус:** принято на этапе проектирования.

Корневой CRL действует 1 год. Оператор подписывает начальный список при первом запуске и планово обновляет его за 30 дней до истечения. При отзыве промежуточного CA оператор подписывает и доставляет обновлённый список сразу.

Такой срок подходит для офлайн-хранения корневого ключа. Плановое обновление можно совместить с ежегодной заменой промежуточного CA. После истечения списка Envoy отклоняет новые mTLS-соединения до применения действующего корневого CRL, поскольку проверка отзыва охватывает всю цепочку.

**Связанный документ:** [технический дизайн первого сценария](first-scenario-design.md#срок-и-обновление-корневого-crl).

## 020. Прекращение TLS-соединений при аварийном отзыве

**Статус:** принято на этапе проектирования.

При аварийном отзыве оператор останавливает проверяющий Envoy. При утечке ключа Web останавливается Envoy Order, при утечке ключа Order — Envoy Web. Перед запуском процесс обновления публикует актуальный CRL. После запуска проверяем отказ по старому сертификату и успешное соединение по новому.

Обновление списка отзыва применяется к новым соединениям. Остановка проверяющего Envoy закрывает также активные соединения. Возобновление TLS-сессий на внутренней связи Web → Order отключено, чтобы новое соединение проходило полную проверку сертификатов. Повторное использование открытого соединения для HTTP-запросов сохраняется.

**Связанный документ:** [технический дизайн первого сценария](first-scenario-design.md#отзыв-сервисного-сертификата-при-утечке-ключа).

**Источник:** [настройки TLS-сессий Envoy](https://www.envoyproxy.io/docs/envoy/latest/api-v3/extensions/transport_sockets/tls/v3/tls.proto.html#envoy-v3-api-msg-extensions-transport-sockets-tls-v3-downstreamtlscontext).

## 021. Публикация комплекта сертификата и ключа для SDS

**Статус:** принято на этапе проектирования.

Каждый новый комплект сертификата и ключа записываем в отдельный каталог версии. Процесс проверяет, что оба файла готовы и соответствуют друг другу, затем одной файловой операцией заменяет `tls-sds.yaml`. Новый файл ссылается на оба файла из нового каталога.

Поэтапная замена двух действующих файлов создала бы промежуток, в котором Envoy мог бы прочитать сертификат и ключ из разных комплектов. Выбрали один момент переключения. Если процесс останавливается до замены файла SDS, Envoy продолжает использовать прежний комплект.

**Связанный документ:** [технический дизайн первого сценария](first-scenario-design.md#применение-обновлённого-сертификата-в-envoy).

**Источник:** [файловый SDS в Envoy](https://www.envoyproxy.io/docs/envoy/latest/configuration/security/secret).

## 022. Обслуживание сертификатов и CRL по этапам

**Статус:** принято для этапа 2 и приёмки выпуска.

В локальном Compose первой заявки оператор запускает обновление сертификатов и загрузку CRL вручную. Команды работают с отдельными каталогами каждого Envoy, проверяют новые файлы и публикуют их через файловый SDS. Инструкция охватывает обновление до истечения и восстановление после истечения. В приёмке первого сценария обе роли после восстановления открывают тот же заказ с его историей.

Сертификаты и сервисный CRL действуют 24 часа, поэтому обслуживать окружение нужно уже при разработке первой заявки. Ручной запуск позволяет восстановить связь в том же окружении. Автоматический запуск, повторы, проверку списка по расписанию и оповещения оператора проверяем в приёмке выпуска.

Это уточняет сроки реализации решений 006, 008, 012, 017 и 018. Сроки действия, проверки доверия и применение через SDS сохраняются.

**Связанные документы:** [технический дизайн первого сценария](first-scenario-design.md#процессы-обновления-сертификатов), [инфраструктурная приёмка выпуска](first-scenario-design.md#инфраструктурная-приёмка-выпуска).

## 023. Сроки сессий и ротация refresh-токенов

**Статус:** сроки и хранение токенов действуют. Политика окна повтора заменена [решением 030](#030-строгая-ротация-refresh-токенов). Защита запросов и выход уточнены в [решении 032](#032-защита-браузерных-запросов-проверкой-origin) и [решении 033](#033-подтверждение-выхода-через-authservice).

Сохраняем абсолютный срок сессии с подтверждения кода, 30 дней для клиента и 8 часов для админа. JWT действует до 5 минут и максимум до конца сессии. После выхода, блокировки или отзыва ранее выданный JWT позволяет клиенту читать свои заказы до истечения. Подача заявки и каждый защищённый запрос админа требуют актуальной проверки сессии и прав. Web API передаёт браузеру JWT и непрозрачный refresh token через отдельные защищённые cookie своего хоста и проверяет CSRF для изменяющих запросов.

При ротации `AuthService` сохраняет точную выданную пару на фиксированные 20 секунд. В пределах окна он возвращает её при повторе, если выданный взамен refresh token ещё действующий. Это позволяет двум вкладкам и браузеру после потерянного ответа продолжить работу. Сервер применяет одно правило при одинаковых токене, состоянии и времени. Тот, кто предъявит перехваченный токен при этих же условиях, получит ту же пару. За пределами окна или после следующей ротации предъявление использованного токена отзывает только эту сессию. Простой отказ в повторе оставил бы в силе новый токен, который мог получить посторонний.

**Связанный документ:** [хранение и ротация токенов](first-scenario-design.md#хранение-и-ротация-токенов).

## 024. Срок, лимиты и повтор отправки кода входа

**Статус:** принято на этапе проектирования.

Используем шестизначный одноразовый код на 10 минут с блокировкой после пяти неверных вводов. На email и назначение входа разрешаем один выпуск в минуту и до пяти за скользящий час. Это ограничивает время жизни кода, попытки подбора и частоту писем. Новый выпуск отменяет предыдущий код. Повторы публикации сохраняют тот же ID, код и срок. Всего до трёх попыток за 4 секунды, с паузами 250 и 750 мс. Если подтверждение потерялось, оставляем поле ввода и предупреждаем о возможной недоставке.

В собственном PostgreSQL `NotiService` хранит одну запись состояния на ID команды. Уникальность и атомарный захват попытки защищают от одновременной отправки дублей, а состояние позволяет разобраться с повтором после перезапуска. После явного временного отказа SMTP возможен один повтор через 5 секунд до истечения кода. При неизвестном исходе команда завершается. Автоматический повтор мог бы продублировать письмо, которое SMTP уже принял. Пользователь может использовать пришедший код или запросить новый в пределах лимитов. Код и тело письма в базе и журналах `NotiService` не сохраняются.

**Связанный документ:** [коды входа и доставка](first-scenario-design.md#коды-входа).

## 025. mTLS для Web → Auth

**Статус:** принято на этапе проектирования.

Web передаёт в `AuthService` коды и refresh tokens и проверяет актуальные сессии и права. Применяем схему, проверенную на стенде Web → Order. Envoy Web проверяет сертификат `auth.ceilings.test`, Envoy Auth требует сертификат `web.ceilings.test`. Оба проверяют цепочку доверия и точный DNS SAN. FastAPI Auth принимает запросы только через Unix-сокет в томе пары Auth и Envoy. `AuthService` отдельно проверяет данные входа, сессии и права пользователя.

Исходящий Envoy Web обслуживает явно настроенные маршруты к Order и Auth. Подключения к БД, брокеру и SMTP идут отдельно. Для Envoy Auth используем тот же порядок выдачи и обслуживания через `step-ca`, SDS и CRL. Общий клиентский сертификат Web обслуживает оба маршрута. При его отзыве доступ восстанавливается после загрузки свежего CRL у обеих принимающих сторон и замены сертификата Web.

**Связанный документ:** [проверка вызывающего сервиса](first-scenario-design.md#проверка-вызывающего-сервиса).

## 026. TLS и права подключений к PostgreSQL и RabbitMQ

**Статус:** принято на этапе проектирования.

Приложения подключаются к БД и брокеру прямо по TLS. Клиент проверяет цепочку доверия и имя сервера по сертификату, сервер проверяет учётные данные клиента и применяет его права. Разные роли ограничивают доступ каждой программы к данным и очередям. Порты остаются во внутренних сетях Compose.

Каждый из трёх экземпляров PostgreSQL доступен своему сервису. Клиент использует `sslmode=verify-full`, база принимает TLS-подключения по `hostssl` с SCRAM-SHA-256. Рабочие роли работают с данными, изменения схемы выполняет отдельная роль миграций. Имена `sslmode` и `hostssl` исторические, протокол соединения — TLS.

RabbitMQ принимает AMQP поверх TLS. У каждого потока свой обменник, очередь и учётные записи издателя и обработчика. `AuthService` публикует команды отправки кодов, публикатор `OrderService` — события заказов. Каждый обработчик `NotiService` читает свою очередь. Конфигурацию обменников и очередей создаём при развёртывании. Раздельные права ограничивают доступ к кодам входа даже при утечке учётных данных обработчика заказов.

**Связанный документ:** [подключения к PostgreSQL и RabbitMQ](first-scenario-design.md#подключения-к-postgresql-и-rabbitmq).

## 027. Ключи подписи JWT

**Статус:** принято на этапе проектирования.

`AuthService` хранит закрытый ключ RSA и подписывает JWT алгоритмом `RS256`. Web проверяет подпись локально по открытым ключам из JWKS и выбирает ключ по `kid`. Это позволяет проверять клиентское чтение при недоступном `AuthService`.

При плановой смене новый открытый ключ сначала загружаем в Web, затем Auth переключает подпись. Старый открытый ключ сохраняем 10 минут после последней подписи, чтобы пятиминутные JWT отработали свой срок. При утечке Web сразу исключает старый ключ из доверенных. Действующая сессия позволяет получить новый JWT по refresh token.

**Связанный документ:** [ключи подписи JWT](first-scenario-design.md#ключи-подписи-jwt).

Для трёх PostgreSQL и RabbitMQ оператор получает отдельные серверные сертификаты в `step-ca`. Проверенный новый комплект загружает перезапуском соответствующего сервера с сохранением тома данных. Принимаем краткий разрыв соединений и проверяем переподключение на новом сертификате.

Пароли и закрытый ключ JWT храним в файлах вне репозитория и монтируем только нужным контейнерам через Compose secrets. Открытый JWKS и корневой сертификат CA раздаём как конфигурацию только для чтения.

## 030. Строгая ротация refresh-токенов

**Статус:** принято на этапе проектирования.

**Дата записи:** 23 ноября 2026 года.

Рассмотрели сохранение и сокращение окна повтора из решения 023. Даже короткое окно позволяет выдать действующую пару по использованному токену, если у сервера нет признака, который отличает потерю ответа от другого повторного предъявления. Выбрали строгую ротацию. Один refresh token можно успешно обменять один раз. Повторное предъявление известного использованного токена отзывает связанную сессию, неизвестный токен отклоняется без изменения сессий. Храним хеши токенов, связанные с сессией. Копию выданной пары для повтора не храним.

Две вкладки в штатном случае координируют обновление. Если Auth зафиксировал обмен, а браузер не получил новые cookie и снова предъявил старый токен, пользователь входит по email-коду заново. При возврате в ту же учётную запись открытая форма сохраняет поля и идентификатор начатой отправки. Если заявка уже была создана, повтор открывает её карточку. Абсолютный срок исходной сессии и правила доступа после отзыва сохраняются.

**Связанный документ:** [хранение и ротация токенов](first-scenario-design.md#хранение-и-ротация-токенов).

## 031. Локальный HTTPS для Web и Mailpit

**Статус:** принято для локального Compose первого сценария.

Web доступен по `https://app.ceilings.test:8443`, Mailpit — по `https://mailpit.ceilings.test:8443`. Оба имени через `hosts` ведут на `127.0.0.1`. HTTPS принимает отдельный входящий listener существующего Envoy Web. Один порт обслуживает два хоста. `Secure` cookie Web без `Domain` отправляются только на хост приложения.

Разработчик устанавливает локальный CA через `mkcert -install` и выпускает один серверный сертификат на оба имени. Envoy получает сертификат и его закрытый ключ, ключ CA остаётся у разработчика. Для внутренних соединений сохраняем `step-ca`. Так обычный браузер доверяет локальному HTTPS, и настройку можно повторить на чистом окружении.

**Связанный документ:** [локальный HTTPS для браузера](first-scenario-design.md#локальный-https-для-браузера).

## 032. Защита браузерных запросов проверкой Origin

**Статус:** принято для первого сценария.

**Дата записи:** 24 ноября 2026 года.

Для изменяющих браузерных запросов Web использует общую проверку точного `Origin`. Он сверяет схему, хост и порт с настроенным адресом приложения. В локальном Compose это `https://app.ceilings.test:8443`. Запросы с отсутствующим, `null` или несовпадающим значением отклоняются до выполнения действия. Правило действует и на запрос и проверку кода, обновление токенов и выход.

Рассмотрели дополнительный токен CSRF. Для первого сценария выбрали строгую проверку одного адреса Web. Поэтому после перезагрузки страницы с истёкшим JWT браузер может обновить вход с действующим refresh token и корректным `Origin`, без восстановления отдельного значения.

## 033. Подтверждение выхода через AuthService

**Статус:** принято для первого сценария.

**Дата записи:** 24 ноября 2026 года.

Web показывает успешный выход и очищает токены из cookie после подтверждения отзыва текущей сессии от `AuthService`. Если подтвердить отзыв не удалось, Web сохраняет cookie для повтора и сообщает об ошибке. Когда первый запрос успел отозвать сессию, но его ответ потерялся, повтор для той же распознанной сессии подтверждает выход. Сессии на других устройствах сохраняются.

Очистка cookie завершает вход в этом браузере. Подтверждение Auth нужно, чтобы сообщить о серверном отзыве. Выход и обновление координируются между вкладками, а приёмка отдельно проверяет запоздалое обновление после выхода.

**Связанный документ:** [технический дизайн и приёмка](first-scenario-design.md#хранение-и-ротация-токенов).
