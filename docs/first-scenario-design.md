# Технический дизайн первого сценария Ceilings

Актуально на 24 ноября 2026 года.

Клиент подтверждает email, отправляет заявку, админ видит её в панели, клиент получает информационное письмо. Согласованный стек — FastAPI, SQLAlchemy, PostgreSQL и Docker. Разделение на сервисы, события и брокер входят в учебные цели.

## Сервисы и данные

| Сервис | Что делает | Свои данные |
|---|---|---|
| Веб-приложение | Показывает кабинет и панель. Обращается к внутренним API от имени текущего пользователя | Собственной БД нет |
| `AuthService` | Выпускает и проверяет коды входа, подтверждает email, управляет ролями и серверными сессиями, выдаёт JWT access tokens и ротирует refresh tokens. Публикует команды отправки кодов | Учётная запись со стабильным ID, подтверждённый email, роли, запросы кодов, сессии и состояние ротации refresh tokens |
| `OrderService` | Проверяет право на действие и доступ к конкретному заказу. Создаёт и читает заказы, ведёт историю | Заказы, контакты для каждого обращения, история, записи для публикации событий |
| `NotiService` | Отправляет коды входа и уведомления о заказах через отдельные обработчики | Задания на письма о заказах и журнал их попыток; ID и состояния обработки команд отправки кодов для распознавания повторов. Содержимое писем с кодами исключено из журналов и истории доставки |

Три независимых экземпляра PostgreSQL с отдельными учётными данными и томами. Каждый сервис с данными подключается только к своей базе. Заказ ссылается на стабильный ID клиента без межбазового внешнего ключа. Замеры, визиты и сметы позже проектируются внутри `OrderService`. Фото заказов и отзывов войдут в выпуск с отзывами вместе с отдельным сервисом файлов и S3-совместимым хранилищем.

## Вход и путь заявки

1. Браузер передаёт веб-приложению email и запрашивает код. Веб-приложение вызывает API `AuthService` с назначением входа. `AuthService` проверяет ограничения, выпускает код, сохраняет одноразовый запрос и публикует команду отправки в RabbitMQ. При временном сбое выполняются ограниченные ретраи той же команды с неизменными ID, кодом и сроком действия. Если подтвердить публикацию не удалось после всех попыток, интерфейс предупреждает, что код может не прийти, и предлагает новый запрос в пределах лимитов, если письма не будет. Поле ввода остаётся доступным: письмо могло быть отправлено несмотря на потерю подтверждения.
2. Браузер передаёт код веб-приложению, оно проверяет его через `AuthService`. Тот создаёт серверную сессию и выдаёт JWT access token и непрозрачный refresh token. Web API устанавливает отдельные защищённые cookie для токенов. Клиентский код открывает существующую учётную запись или создаёт подтверждённую запись. Административный код отдельный и доступен только действующей персональной записи админа. Служебная команда создаёт первую запись. На разных устройствах могут быть отдельные сессии. При утрате почты оператор проверяет личность, меняет email той же записи служебной командой и отзывает прежние коды и сессии. Стабильный ID сохраняет авторство в истории.
3. Клиент отправляет форму с идентификатором отправки. Серверная часть веб-приложения (Web API) локально проверяет подпись JWT, срок действия, издателя и получателя. Для подачи заявки сохраняется проверка актуальной сессии и прав через `AuthService`. Если эту проверку выполнить невозможно, заявка не создаётся. Для последующих клиентских функций актуальную проверку согласуем при их проектировании. Обычное клиентское чтение не требует обращения в `AuthService` на каждый запрос.
4. Веб-приложение вызывает внутренний API `OrderService` и передаёт поля формы, идентификатор отправки, подтверждённые ID, роль и email. Web API формирует доверенный серверный контекст по проверенному JWT и, когда требуется актуальная проверка, ответу `AuthService`. Произвольные поля формы и заголовки браузера не задают личность или роль. `OrderService` проверяет вызывающий сервис, роль клиента и право на действие, назначает владельцем подтверждённый ID и сохраняет заявку. Ответ содержит ID заказа и исход отправки. Веб-приложение открывает карточку созданной или уже существующей заявки либо показывает ошибку.
5. Админ открывает панель. Web API локально проверяет JWT и при каждом защищённом административном запросе, включая чтение, проверяет актуальную сессию и права через `AuthService`. Если проверка недоступна или права отозваны, запрос не разрешается. При успешной проверке веб-приложение запрашивает список или карточку в `OrderService`. Тот проверяет право чтения и возвращает сохранённую заявку сразу после фиксации транзакции. Чтение клиентом ограничено его собственным ID. Для повторной заявки веб-приложение запрашивает у `OrderService` имя и телефон из последней поданной заявки. Клиент может их изменить. Email всегда берётся из учётной записи.

## Аутентификация и чтение заказов

Для клиентов и администраторов согласованы короткоживущие JWT access tokens, refresh tokens с ротацией и серверные сессии в `AuthService`. JWT подтверждает личность и содержит сведения на момент выдачи. Успешная локальная проверка не доказывает, что сессия или права по-прежнему действуют. Для критических операций нужны и корректный JWT, и успешная актуальная проверка через `AuthService`. Для админа актуальная проверка обязательна на каждом защищённом запросе, включая чтение.

Абсолютный срок сессии отсчитывается от подтверждения кода и составляет 30 дней для клиента и 8 часов для админа. Срок access token составляет до 5 минут и ограничен концом сессии. Обновление токенов сохраняет исходный абсолютный срок.

При обычном клиентском чтении Web API проверяет JWT локально и передаёт доверенный контекст в `OrderService`. После выхода, блокировки или отзыва ранее выданный access token позволяет прочитать свои заказы до его истечения, то есть ещё не более 5 минут. Обновление токенов и операции с актуальной проверкой, включая подачу заявки, прекращаются сразу для недействительной сессии. Недоступность `AuthService` сохраняет возможность обычного чтения с действительным JWT. Для обновления токенов и защищённых запросов админа требуется доступный `AuthService`.

`OrderService` владеет данными заказов и проверяет принадлежность при самом чтении. В текущем дизайне поле владельца называется `owner_id`, поэтому запрос карточки ограничивается условием `WHERE id = :order_id AND owner_id = :authenticated_user_id`. Идентификатор пользователя приходит из доверенного серверного контекста. Отдельный запрос «можно ли читать заказ» перед чтением не нужен. Индекс первичного ключа позволяет найти заказ по ID без перебора всех заказов; проверяется также совпадение владельца. Списки и история ограничены тем же владельцем.

Идентификатор активного заказа и разрешения на конкретные заказы в JWT не включаем. Чтение остаётся в `OrderService`. Redis для обхода сервиса или проверки принадлежности не вводим; кеш истории не принят в работу. Сначала делаем компактные ответы для экрана, подходящие индексы и исключаем лишние запросы. Решения о кешировании или масштабировании принимаем по результатам нагрузочной проверки.

## Хранение и ротация токенов

Web API устанавливает токены в две cookie своего хоста без `Domain`, с атрибутами `HttpOnly`, `Secure` и `SameSite=Lax`. Браузер передаёт их по HTTPS. Web API проверяет JWT локально, а непрозрачный refresh token передаёт в `AuthService` при обновлении через `POST /auth/refresh`. При окончательном отказе в продолжении сессии Web API очищает cookie. При временном сбое обновления интерфейс показывает ошибку и позволяет повторить действие, сохраняя состояние входа.

**Защита изменяющих браузерных запросов.** Web применяет общую проверку `Origin` до выполнения действия. Она действует на запрос и подтверждение кода, обновление, выход, подачу заявки и последующие изменяющие действия из кабинета или панели. Допустимый `Origin` задан в конфигурации окружения целиком, включая схему, хост и порт. В локальном Compose это `https://app.ceilings.test:8443`. Заголовок назначения `Host` и переадресованные заголовки запроса не задают значение для сравнения. Отсутствующий, `null` или несовпадающий `Origin` отклоняется. Отдельный CSRF-токен не используем. После перезагрузки с истёкшим JWT браузер может обновить вход с действующей cookie refresh token и корректным `Origin`. [Решение 032](decisions.md#032-защита-браузерных-запросов-проверкой-origin)

**Выход.** Web показывает успешный выход и очищает обе cookie после подтверждения от `AuthService`, что текущая сессия отозвана. Если Auth недоступен или подтверждение потерялось, Web сохраняет cookie для повтора и показывает «Не удалось завершить сеанс. Попробуйте ещё раз». Повтор с той же распознанной сессией подтверждает выход, если она уже была отозвана. В браузере с общей блокировкой вкладок выход и обновление используют ту же блокировку. Проверяем, что запоздалое обновление не возвращает интерфейс в кабинет или панель после подтверждённого выхода. [Решение 033](decisions.md#033-подтверждение-выхода-через-authservice)

**Строгая ротация без окна повтора.** Каждый refresh token можно успешно обменять один раз. `AuthService` хранит хеш текущего токена и хеши использованных токенов со связью с сессией до её окончания. Запросы одной сессии обрабатываются последовательно. Проверка сессии и роли, замена хеша и отметка об использовании старого токена происходят в одной транзакции. Новая пара возвращается после фиксации транзакции.

Повторное предъявление известного использованного токена отзывает связанную с ним сессию и не выдаёт токены. Неизвестный токен отклоняется без изменения сессий. Истечение сессии, блокировка, отзыв или отсутствие требуемой роли исключают обновление. Ротация сохраняет исходный абсолютный срок сессии. [Решение 030](decisions.md#030-строгая-ротация-refresh-токенов)

| Ситуация | Что видит сервер и как отвечает | Что видит пользователь |
|---|---|---|
| Двум вкладкам нужно обновление | Одна вкладка удерживает общую блокировку на время обновления. Вторая после ожидания проверяет доступ с текущими cookie и пропускает обновление, если доступ уже восстановился. | Обе вкладки продолжают работу. |
| Ответ на обновление потерялся | Если браузер применил новые cookie, он продолжает с ними. Если Auth не зафиксировал обмен, `R0` остаётся действующим. Если обмен зафиксирован, а браузер снова предъявляет `R0`, Auth отзывает сессию. | Таймаут сам по себе не завершает вход. После подтверждённого отзыва нужен новый код. |
| Два запроса с `R0` всё же дошли до Auth или использованный `R0` предъявили позже | Проходит ровно один обмен. Повтор отзывает эту сессию, её новый refresh token больше не обновляет токены. | Кабинет или панель снова запрашивает email-код. Сессии на других устройствах сохраняются. |

При поддержке общей блокировки вкладок браузер координирует обновление и выход. Сервер применяет то же правило одноразового обмена, если запросы всё же пришли одновременно.

Если во время заполнения заявки понадобился новый вход, по возвращении в ту же учётную запись в открытой форме восстанавливаются поля и идентификатор уже начатой отправки. Клиент сам решает, повторять ли отправку. При неизвестном результате исходной отправки повтор использует те же данные и идентификатор. Если заказ уже создан, открывается его карточка. Вход в другую учётную запись не переносит туда форму или незавершённую отправку.

### Ключи подписи JWT

`AuthService` подписывает access token закрытым ключом RSA с алгоритмом `RS256`. Ключ доступен только `AuthService` и оператору развёртывания. Web получает локальный файл JWKS только с открытыми ключами и выбирает ключ по `kid`. Web принимает только ожидаемый алгоритм, отклоняет неизвестный `kid` и проверяет подпись, срок, издателя и получателя. Для этих проверок сетевой вызов к `AuthService` не нужен. [Формат JWKS и `kid`](https://www.rfc-editor.org/rfc/rfc7517.html#section-4.5) · [Требования к проверке JWT](https://www.rfc-editor.org/rfc/rfc8725.html#section-3.1)

1. При плановой смене оператор готовит новую пару и добавляет открытый ключ в локальный JWKS. Web загружает набор, в котором доступны оба ключа.
2. Когда Web загрузил новый ключ, оператор переключает `AuthService` на подпись новым ключом и `kid`. JWT со старой подписью проверяются до своего `exp`.
3. Через 10 минут после последней подписи старым ключом оператор удаляет его из JWKS. Access token действует максимум 5 минут, оставшееся время даёт запас на переключение.

При утечке закрытого ключа Auth прекращает его использовать, а оператор сразу удаляет соответствующий открытый ключ из доверенных на Web. JWT с этим `kid` отклоняются после загрузки обновлённого набора даже до `exp`. Браузер может получить новый JWT через обычное обновление, если серверная сессия и refresh token ещё действуют и новый ключ уже загружен. [Решение 027](decisions.md#027-ключи-подписи-jwt)

## Проверка вызывающего сервиса

**Согласованы Envoy-sidecar у веб-приложения и у `OrderService`, mTLS между ними и Unix-сокет от входящего Envoy к FastAPI `OrderService`.** Путь запроса: `Web API → Unix-сокет → Envoy веб-приложения → mTLS → Envoy OrderService → Unix-сокет → FastAPI`. Envoy Web предъявляет клиентский сертификат с DNS SAN `web.ceilings.test` и проверяет цепочку доверия и точное DNS SAN `order.ceilings.test` у Envoy Order. Envoy Order предъявляет серверный сертификат с DNS SAN `order.ceilings.test`, требует клиентский сертификат и проверяет его цепочку доверия и точное DNS SAN `web.ceilings.test`. **Согласован Unix-сокет для Web API → собственный исходящий Envoy.** Сокет находится в отдельном Docker-томе, доступном только этой паре контейнеров, с ограниченными файловыми правами. Этот том не используется для сокетов Order или Auth. У исходящего прокси нет доступного другим контейнерам TCP-входа для вызовов от имени Web. Доступ к этому прокси позволяет использовать сервисную личность Web, поэтому проверяем изоляцию сокета, а не только хранение сертификата.

Envoy `OrderService` передаёт запросы через Unix-сокет в выделенном Docker-томе, доступном только этой паре контейнеров. FastAPI не слушает TCP-порт; права на сокет ограничивают локальный доступ. Это закрывает прямой сетевой вход в API в обход Envoy. Использование Unix-сокета для входящих HTTP-запросов не отключает исходящие сетевые соединения приложения, в том числе подключение драйвера к PostgreSQL. Сеть контейнера `OrderService` отключать нельзя. В приёмке проверяем одновременно отсутствие прямого сетевого входа в API и успешную работу с его БД, а также восстановление соединения через сокет после перезапуска FastAPI.

Envoy — инфраструктурный компонент соответствующего сервиса. Для внутренних сертификатов учебного окружения выбран `step-ca`. Сервисные сертификаты и ключи разделяются по сторонам соединения. Закрытые ключи передаются как секреты вне репозитория. Необходимость общего порядка управления сертификатами и секретами согласована; конкретные механизмы выпуска, хранения, замены и прекращения доверия обсуждаются отдельно ниже. [Envoy TLS и проверка SAN](https://www.envoyproxy.io/docs/envoy/latest/api-v3/extensions/transport_sockets/tls/v3/common.proto.html)

**Web → Auth также использует mTLS через Envoy.** Путь запроса — `Web API → Unix-сокет → Envoy Web → mTLS → Envoy Auth → Unix-сокет → FastAPI Auth`. Envoy Web проверяет цепочку доверия и точное имя `auth.ceilings.test` в DNS SAN. Envoy Auth требует клиентский сертификат и проверяет цепочку и точное имя `web.ceilings.test` в DNS SAN. FastAPI Auth слушает только Unix-сокет, доступный в отдельном томе контейнерам Auth и его Envoy. `AuthService` отдельно проверяет коды, токены, состояние сессий и права пользователя. Сервисная идентичность Web даёт доступ к API, которое нужно для входа и проверок сессии. [Решение 025](decisions.md#025-mtls-для-web--auth)

Web API явно направляет внутренние HTTP-вызовы к Order и Auth через свой исходящий Envoy. Подключения приложений к PostgreSQL, RabbitMQ и SMTP проходят отдельно со своими настройками защиты. Web использует один сервисный сертификат на обоих маршрутах. При его отзыве обоим входящим Envoy требуется свежий CRL, а Web требуется новый сертификат.

Envoy Order принимает действительный клиентский сертификат с DNS SAN `web.ceilings.test` и отклоняет соединение без клиентского сертификата. Envoy Web отклоняет серверный сертификат с другим DNS SAN вместо `order.ceilings.test` даже при доверенной цепочке. Отдельно проверяем сертификат другого сервиса от того же CA. Он должен быть отклонён из-за несовпадения SAN до обработки запроса в FastAPI. Проверяем также, что порт FastAPI недоступен напрямую и что запрос с клиентской ролью даже через доверенный шлюз не открывает панель.

## Управление сертификатами и секретами — выбран step-ca, механизмы уточняются

**Выбран `step-ca` как внутренний CA учебного окружения.** Причины выбора, альтернативы и последствия записаны в [решении 004](decisions.md#004-step-ca-для-внутренних-сертификатов-учебного-окружения). Автоматическая идентификация процессов через SPIRE и общая платформа секретов Vault на текущем этапе не выбраны. `step-ca` — инфраструктурный компонент, состав четырёх прикладных сервисов не меняется.

### Назначение сервисных сертификатов

Для внутреннего mTLS используем по одному сервисному сертификату на Envoy. Локальный входящий HTTPS Envoy Web использует отдельный сертификат для браузера. Сертификат Web с DNS SAN `web.ceilings.test` имеет назначение `clientAuth` для вызовов Order и Auth и для обновления в `step-ca`. Сертификаты Order (`order.ceilings.test`) и Auth (`auth.ceilings.test`) имеют `serverAuth` для входящих вызовов Web и `clientAuth` для обновления в `step-ca`. При обновлении процесс предъявляет текущий сертификат своего Envoy как клиент CA. [Обновление в Smallstep](https://smallstep.com/docs/step-ca/basic-certificate-authority-operations/#renew-a-certificate) · [Решение 011](decisions.md#011-назначение-сертификатов-web-и-order)

### Первоначальная выдача

Первую выдачу разрешает оператор развёртывания. Это человек, который настраивает окружение и имеет доступ к выпуску сертификатов. Полномочиями оператора управляют отдельно от роли «Админ» в панели заказов. [Решение 005](decisions.md#005-первоначальная-выдача-сертификатов-по-разрешению-оператора)

1. При развёртывании служебная команда создаёт закрытый ключ для конкретного Envoy и формирует запрос на сертификат (CSR). Закрытый ключ остаётся в выделенном хранилище этого Envoy. В CA он не передаётся.
2. Оператор определяет разрешённое имя сервиса в SAN и выпускает короткоживущий одноразовый токен через JWK provisioner в `step-ca`. Токен ограничен разрешённым именем и привязан к конкретному CSR. Полномочия выпуска токенов остаются у оператора.
3. Команда развёртывания проверяет `step-ca` по заранее установленному корневому сертификату и отправляет CSR и токен. `step-ca` проверяет разрешение и подписывает сертификат. Envoy получает сертификат и использует его со своим ключом. [Токены выдачи Smallstep](https://smallstep.com/docs/step-cli/reference/ca/token/)

### Срок сервисных сертификатов и начало обновления

Сервисные сертификаты Envoy в учебном окружении действуют 24 часа. Первую попытку планового обновления назначаем за 8 часов до истечения текущего сертификата. Запас времени позволяет повторить обновление и восстановить доступ к `step-ca` при временном сбое. [Решение 006](decisions.md#006-срок-сервисных-сертификатов-и-начало-обновления)

### Применение обновлённого сертификата в Envoy

Для планового обновления используем файловый SDS. Процесс обновления получает сертификат у `step-ca` и публикует готовый комплект сертификата и соответствующего ключа в файловом источнике SDS. Envoy загружает обновление в работающий процесс и предъявляет новый сертификат при новых TLS-рукопожатиях. Каждый новый комплект записываем в отдельный каталог версии. После записи и проверки обоих файлов процесс готовит новый `tls-sds.yaml` со ссылками на сертификат и ключ из одного каталога и атомарно заменяет действующий файл SDS в той же файловой системе. Если процесс прерывается до замены, действующий файл по-прежнему указывает на прежний комплект. [Решение 021](decisions.md#021-публикация-комплекта-сертификата-и-ключа-для-sds) [Документация Envoy о файловом SDS](https://www.envoyproxy.io/docs/envoy/latest/configuration/security/secret#key-rotation) · [Решение 007](decisions.md#007-плановое-обновление-сертификатов-envoy-через-файловый-sds)

### Процессы обновления сертификатов

**На этапе 2, в локальном Compose первой заявки, оператор запускает обновление сертификатов и загрузку CRL вручную по инструкции.** Команды обновления запускаются отдельно для каждого Envoy. Для Web, Order и Auth используются отдельные контейнеры из одного образа. Каждый Envoy читает свой каталог. Соответствующая команда обновления имеет доступ к закрытому ключу только своего Envoy и может записывать только в его каталог. [Решение 022](decisions.md#022-обслуживание-сертификатов-и-crl-по-этапам)

Инструкция этапа 2 показывает, как проверить сроки сертификатов и `nextUpdate` локальных CRL, как обновить комплект до истечения и как восстановить связь после истечения. Запуск команды вручную использует те же проверки и файловый SDS. Для выпуска каждый процесс следит за сроком своего сертификата и автоматически запрашивает обновление за 8 часов до истечения. [Решение 008](decisions.md#008-отдельный-процесс-обновления-для-каждого-envoy)

При каждом плановом обновлении сертификата Envoy используем `step ca rekey`. Процесс создаёт новую пару ключей и получает сертификат на новый открытый ключ. После проверки соответствия сертификата ключу публикует их одним комплектом для файлового SDS. При сбое действующий комплект сохраняется. Плановое обновление завершает использование прежнего ключа самим Envoy, а при компрометации отдельно применяем активный отзыв. [Команда step ca rekey](https://smallstep.com/docs/step-cli/reference/ca/rekey/) · [Решение 015](decisions.md#015-новый-ключ-envoy-при-каждом-плановом-обновлении)

### Хранение и восстановление ключей и CA

Ключи и сертификаты Envoy хранятся обычными файлами в защищённых каталогах файловой системы вне репозитория. У каждой пары Envoy и процесса обновления свой постоянный каталог. Envoy подключает свой каталог для чтения, процесс обновления — для чтения и записи. При пересоздании контейнеров файлы сохраняются. Если сервисный ключ потерян, создаём новую пару и повторяем первую выдачу для имени сервиса с тем же доверенным корнем. [Решение 009](decisions.md#009-хранение-ключей-и-восстановление-ca)

Запущенный `step-ca` использует промежуточный ключ, а корневой ключ хранится отдельно, в зашифрованном виде вне работающего окружения. Для ключа выдачи токенов используется отдельный пароль `operator_password`, доступный только команде `pki-operator`. Контейнер `step-ca` получает `ca_password` для запуска и хранит только зашифрованный материал ключа оператора и его открытый ключ. Публичный корневой сертификат предоставляется Envoy и командам, которые проверяют CA. Собственная база `step-ca` хранит состояние выпуска, отзыва и использованных токенов отдельно от файлов Envoy. [Ключи CA](https://smallstep.com/docs/step-ca/certificate-authority-server-production/#safeguard-your-root-and-intermediate-keys) · [База step-ca](https://smallstep.com/docs/step-ca/configuration/#databases)

Зашифрованная резервная копия рабочего CA включает промежуточный закрытый ключ и сертификат, публичный корневой сертификат, конфигурацию `step-ca` с настройками и файлами выдачи и согласованный снимок базы. Корневой ключ и закрытый ключ выдачи токенов сохраняются в отдельном защищённом резерве, если их рабочие копии ведутся отдельно от `step-ca`. Пароли для восстановления хранятся отдельно от зашифрованных копий. Зашифрованную копию CA храним на внешнем диске отдельно от компьютера, на котором работает Compose. После копирования отключаем диск.

### Недоступность CA и истечение сертификата

При сбое обновления действующий комплект сохраняется. На этапе 2 оператор видит причину сбоя и повторяет команду после восстановления CA. В режиме выпуска процесс записывает причину в журнал и повторяет запрос каждые 5 минут, пока текущий сертификат действителен. Если обновление не удалось за 1 час до истечения, процесс предупреждает оператора. После восстановления CA очередная попытка получает и применяет новый сертификат через файловый SDS.

После истечения текущий сертификат отклоняется при новых полных TLS-рукопожатиях. Уже открытые соединения могут продолжать работу. Для просроченного сертификата требуется новая выдача по одноразовому разрешению оператора по согласованной процедуре. Обновление просроченного сертификата через `step-ca` оставляем отключённым. [Обновление после истечения в Smallstep](https://smallstep.com/docs/step-ca/renewal/#renewal-after-expiry-for-intermittently-connected-devices) · [Решение 012](decisions.md#012-сбой-обновления-и-истечение-сервисного-сертификата)

### Отзыв сервисного сертификата при утечке ключа

При компрометации ключа Envoy используем активный отзыв. Оператор отзывает в `step-ca` все ещё действующие сертификаты, выпущенные для этого ключа. `step-ca` блокирует их обновление. Проверяющий Envoy загружает актуальный подписанный CRL (список серийных номеров отозванных сертификатов) из локального файла и отклоняет отозванные сертификаты на новых соединениях. Для ключа Web список применяют Envoy Order и Envoy Auth. Для ключа Order или Auth список применяет Envoy Web. [CRL в Smallstep](https://smallstep.com/docs/step-ca/certificate-authority-server-production/#consider-active-revocation) · [Проверка CRL в Envoy](https://www.envoyproxy.io/docs/envoy/latest/api-v3/extensions/transport_sockets/tls/v3/common.proto.html)

При аварийном отзыве оператор останавливает проверяющие Envoy, чтобы закрыть установленные соединения. При утечке ключа Web это Envoy Order и Envoy Auth. При утечке ключа Order или Auth это Envoy Web. Процесс обновления публикует актуальный CRL до запуска остановленных Envoy. Для скомпрометированного Envoy создаём новый ключ и повторяем первую выдачу под прежним корнем. После запуска проверяем, что старый сертификат отклоняется, а новый проходит.

На внутренних связях Web → Order и Web → Auth возобновление TLS-сессий отключено. Каждое новое соединение проходит полное рукопожатие и проверку сертификатов. Уже открытое соединение может обслуживать несколько HTTP-запросов. Плановое обновление сертификатов по-прежнему применяется через файловый SDS. [Настройки TLS-сессий Envoy](https://www.envoyproxy.io/docs/envoy/latest/api-v3/extensions/transport_sockets/tls/v3/tls.proto.html#envoy-v3-api-msg-extensions-transport-sockets-tls-v3-downstreamtlscontext) · [Решение 020](decisions.md#020-прекращение-tls-соединений-при-аварийном-отзыве) Эта процедура относится к утечке ключа сервиса. [Решение 013](decisions.md#013-активный-отзыв-сервисных-сертификатов)

### Восстановление после компрометации CA

При утечке промежуточного ключа оператор приостанавливает затронутые соединения и закрывает старые TLS-сессии. Если корневой ключ защищён, он подписывает новый промежуточный сертификат и CRL с отзывом старого промежуточного сертификата. Envoy проверяют отзыв по всей цепочке. Для нового промежуточного CA настраиваем `step-ca` и повторяем первую выдачу сертификатов Web и Order. Прекращаем принимать старую цепочку как на соединениях между сервисами, так и для обновления в CA. Обычная плановая замена промежуточного ключа сама по себе этого не обеспечивает. [Проверка CRL в Envoy](https://www.envoyproxy.io/docs/envoy/latest/api-v3/extensions/transport_sockets/tls/v3/common.proto.html) · [Замена промежуточного CA в Smallstep](https://smallstep.com/docs/step-ca/certificate-authority-server-production/#rotating-an-intermediate-ca)

При утечке корневого ключа оператор приостанавливает затронутые соединения и закрывает старые TLS-сессии. В доверенном окружении создаёт новый корневой и промежуточный CA. Новый публичный корневой сертификат распространяет через доверенный канал развёртывания в Envoy, процессы обновления и инструменты выдачи. Старый корень удаляется из доверия. Для Web и Order заново выпускаются сертификаты. Допускаем простой на время переключения. Соединения возобновляются после проверки новой цепочки. [Решение 014](decisions.md#014-восстановление-доверия-после-компрометации-ca)

### Плановая замена ключей CA

Промежуточный сертификат действует 1 год, корневой — 5 лет. Оператор начинает плановую замену за 30 дней до истечения соответствующего сертификата.

При плановой замене промежуточного CA оператор создаёт новый ключ и подписывает новый промежуточный сертификат прежним корневым ключом. `step-ca` выдаёт новые сервисные сертификаты по новой цепочке. Envoy переходят на неё при штатном обновлении, а сертификаты прежней цепочки остаются действительными до истечения своего срока.

При плановой замене корневого CA оператор сначала добавляет новый корень в доверенные у Envoy, процессов обновления и инструментов выдачи. Затем переключает выпуск на новую цепочку и проверяет mTLS и обновление сертификатов. После перехода всех участников оператор удаляет прежний корень из доверия. Временное доверие обоим корням допустимо при плановой замене. При компрометации применяется отдельная процедура восстановления доверия. [Плановая замена CA в Smallstep](https://smallstep.com/docs/step-ca/certificate-authority-server-production/#rotating-ca-certificates) · [Решение 016](decisions.md#016-плановая-замена-ключей-ca)

### Доставка списков отзыва в Envoy

При отзыве сервисного сертификата `step-ca` формирует обновлённый подписанный CRL. Команды обновления Web, Order и Auth получают список, проверяют подпись и срок действия и публикуют проверенные файлы для своих Envoy. На этапе 2 их запускает оператор, для выпуска загрузка выполняется также по расписанию. Envoy применяет локальные списки через файловый SDS и использует их при проверке новых TLS-соединений. Для проверки отзыва по всей цепочке комплект содержит списки от всех нужных издателей. [Настройки CRL в Smallstep](https://smallstep.com/docs/step-ca/configuration/) · [Проверка CRL в Envoy](https://www.envoyproxy.io/docs/envoy/latest/api-v3/extensions/transport_sockets/tls/v3/common.proto.html)

При аварийном отзыве оператор запускает загрузку сразу и проверяет, что Envoy применил список и отклоняет соединение с отозванным сертификатом. CRL, подписанный корневым ключом для отзыва промежуточного сертификата, оператор доставляет через доверенный канал развёртывания. [Решение 017](decisions.md#017-доставка-списков-отзыва-в-envoy)

### Срок и обновление сервисного CRL

CRL для сервисных сертификатов действует 24 часа. `step-ca` перевыпускает его каждые 8 часов и при каждом отзыве. На этапе 2 оператор запускает загрузку свежего списка. При сбое загрузки сохраняется последняя действующая локальная копия до её `nextUpdate`. Для выпуска процессы Web и Order проверяют обновление раз в минуту, журналируют сбои и предупреждают оператора, если за час до истечения свежей копии ещё нет. [Настройки CRL в Smallstep](https://smallstep.com/docs/step-ca/configuration/) · [Решение 018](decisions.md#018-срок-сервисного-crl-и-поведение-при-истечении)

По достижении `nextUpdate` Envoy отклоняет новые mTLS-соединения до применения действующего списка. Уже открытые соединения могут продолжать работу. При известной компрометации их закрываем отдельным действием по процедуре активного отзыва. Эти интервалы относятся к CRL для сервисных сертификатов.

### Срок и обновление корневого CRL

Корневой CRL содержит отозванные промежуточные сертификаты. При первом запуске оператор подписывает начальный корневой список, даже если отозванных сертификатов ещё нет. Список действует 1 год. За 30 дней до его истечения оператор подписывает новый корневым ключом и доставляет его через доверенный канал развёртывания. При отзыве промежуточного сертификата оператор подписывает и доставляет новый список сразу. [Решение 019](decisions.md#019-срок-корневого-crl-и-поведение-при-истечении)

После истечения корневого CRL новые mTLS-соединения отклоняются до загрузки действующего списка. Правило действует и при свежем сервисном CRL, поскольку Envoy проверяет отзыв по всей цепочке. [Проверка CRL в Envoy](https://www.envoyproxy.io/docs/envoy/latest/api-v3/extensions/transport_sockets/tls/v3/common.proto.html)

### Открытые детали жизненного цикла

До запуска окружения нужно согласовать оставшиеся детали. Envoy применяет TLS-настройки, а выдачу и замену организуем отдельно. Прекращение доверия к старому сертификату требует отдельного действия при компрометации.
- Для выпуска уточнить, как процессы отслеживают пороги обновления и как оператор получает предупреждение.
- При реализации проверяем поддержку CRL в выбранной версии `step-ca`. Документация отмечает встроенную генерацию как экспериментальную. [Параметры CRL в Smallstep](https://smallstep.com/docs/step-ca/configuration/)

## Минимальные записи и конкурентные запросы

- **Сервис доступа.** Для учётной записи нужны ID, email, признак подтверждения и действующие роли. Для запроса кода — email, назначение входа, защищённое представление кода, время выпуска и истечения, состояние и счётчик неверных вводов. Для сессии — ID, ID учётной записи, тип доступа, абсолютный срок и признак отзыва. Для ротации нужны хеши текущего и использованных refresh tokens со связью с сессией. JWT содержит сведения для проверки подписи, срока, издателя и получателя и связи с личностью и сессией. Данные о конкретных заказах остаются в `OrderService`.
- **Заказ.** ID и номер, `owner_id`, имя, телефон, адрес, необязательные поля формы, стадия «Новая заявка», время создания и признак закрытия `closed_at`. Храним `submission_id` и отпечаток исходных нормализованных полей формы. Email и роль проверяются отдельно. Изменение контактов впоследствии не меняет отпечаток первой отправки.
- **История и публикация.** Событие создания хранит свой ID, ID заказа, тип, время и автора. Запись публикации использует тот же ID события и хранит данные для письма и состояние публикации. Заказ, история и запись публикации сохраняются одной транзакцией.
- **Уведомления.** Для письма о заказе сохраняются одно задание на `event_id`, адрес получателя, данные письма, состояние и срок следующей попытки. Для каждой попытки сохраняются время и результат. Для кода достаточно уникального `command_id`, состояния, номера попытки, срока кода и времени следующей попытки при временном отказе. Код, тело письма и исходная команда в PostgreSQL `NotiService` не сохраняются.

Предлагаемые ограничения PostgreSQL в базе `OrderService` — уникальность `(owner_id, submission_id)` для всех заказов и уникальный частичный индекс по `owner_id WHERE closed_at IS NULL` для активных. Признак закрытия обновляется вместе со стадией при закрытии. [Частичные индексы PostgreSQL](https://www.postgresql.org/docs/current/indexes-partial.html)

После проверки доступа и полей `OrderService` пытается вставить заказ через `INSERT … ON CONFLICT DO NOTHING RETURNING id`. При успехе добавляет событие истории и запись публикации в ту же транзакцию и отвечает после фиксации. Если вставка не вернула строку, следующий запрос чтения в `READ COMMITTED` сначала ищет заказ по паре `(owner_id, submission_id)`. При совпадении отпечатка возвращает тот же заказ, при различии возвращает конфликт идентификатора. Если такой пары нет, ищет действующий заказ и возвращает конфликт со ссылкой на него. Если он успел закрыться до чтения, повторяет операцию в новой транзакции в пределах ограниченного числа попыток. При двух одинаковых запросах индексы допускают одну вставку и оба запроса получают один ID. При двух разных запросах одного клиента частичный индекс допускает одну вставку, второй запрос получает конфликт. [Изоляция транзакций PostgreSQL](https://www.postgresql.org/docs/current/transaction-iso.html)

## Доставка писем

Используем один RabbitMQ с двумя отдельными очередями. Очередь кодов получает команды от `AuthService`, очередь писем о заказах получает события от `OrderService`. В `NotiService` у каждой очереди свой обработчик. Очередь кодов обрабатывается независимо от накопившихся писем о заказах.

### Коды входа

Маршрут — `AuthService → RabbitMQ → NotiService → SMTP`. Команда содержит уникальный `command_id`, адрес получателя, код и момент истечения срока действия, заданный `AuthService`.

**Выпуск и проверка.** Код из 6 цифр живёт 10 минут с выпуска и допускает одно успешное использование. Пятый неверный ввод блокирует этот код. Параллельные вводы учитывают общий счётчик, а одновременный ввод верного кода создаёт одну сессию. Для каждого email и назначения входа `AuthService` разрешает выпуск не чаще раза в минуту и до пяти раз за скользящий час. Проверка лимитов, отмена предыдущего кода и сохранение нового выполняются атомарно. Отказ по лимиту сохраняет состояние текущего кода. Выпуск учитывается в лимите, даже если подтверждение публикации потеряно. Административный код и код кабинета проверяются каждый для своего назначения.

**Адрес получателя.** Auth использует канонический нормализованный email для учётной записи, а для SMTP передаёт адрес с ASCII-представлением домена. Поэтому кириллический домен можно ввести как в Unicode, так и в Punycode. Для адреса с Unicode до `@` форма объясняет ограничение текущей доставки и отклоняет запрос до выпуска кода. Служебная команда создания админа использует то же правило. Noti преобразует кириллический домен и в ранее поставленной команде. Недопустимый адрес в старой команде завершает обработку ошибкой до соединения со SMTP. [Нормализация email и `ascii_email`](https://github.com/JoshData/python-email-validator#return-value)

**Публикация.** `AuthService` публикует команду напрямую, без outbox. Допускается до трёх попыток, включая первую, в пределах 4 секунд на публикацию целиком. Паузы перед повторами составляют 250 и 750 мс в пределах этого бюджета. Повторы используют тот же `command_id`, код и срок. По истечении срока кода попытки прекращаются. Подтверждение маршрутизированной команды означает, что её принял RabbitMQ. При исчерпании попыток интерфейс предупреждает, что код может не прийти, и оставляет поле ввода доступным. Если письма нет, пользователь может запросить новый код в пределах лимитов. После падения `AuthService` между выпуском и публикацией восстановление начинается с нового запроса пользователя. [Подтверждения публикации RabbitMQ](https://www.rabbitmq.com/docs/reliability)

**Обработка команды.** `NotiService` использует `UNIQUE(command_id)` в своей базе PostgreSQL. Обработчик атомарно отмечает начало попытки до обращения к SMTP. При одновременной доставке копий только один обработчик получает право на эту попытку. Запись с завершённым исходом пропускается при повторной доставке. До завершения доставки команда остаётся доступной в RabbitMQ для восстановления после падения. `NotiService` проверяет срок перед каждой попыткой и завершает просроченную команду без отправки. Письмо с отменённым кодом может прийти позже нового. `AuthService` принимает только действующий код для этого email и назначения.

**Результат SMTP.** При подтверждённом временном отказе `NotiService` сохраняет состояние и делает один повтор через 5 секунд, если срок кода ещё не истёк. При подтверждённом принятии письма команда завершается. Если ответ SMTP потерян после возможного принятия письма или процесс упал во время отправки и исход установить невозможно, `NotiService` завершает команду со статусом «Исход неизвестен». Автоматическая повторная отправка в этом случае могла бы продублировать письмо. Если письмо пришло, действующий код можно ввести. Если письма нет, пользователь запрашивает новый код в пределах лимитов. [Финальный ответ SMTP](https://www.rfc-editor.org/rfc/rfc5321.html#section-4.5.3.2.6)

Noti удерживает блокировку PostgreSQL на `command_id` до завершения обработки текущей доставки. Отметку о начале SMTP-попытки сохраняет отдельной транзакцией до сетевого вызова. После явного временного отказа сохраняет время повтора и оставляет сообщение неподтверждённым, чтобы RabbitMQ сохранил полезную нагрузку. После перезапуска обработчик ждёт оставшееся время по записи в PostgreSQL. Если там отмечено начало попытки без результата, он записывает неизвестный исход. `ACK` отправляется после фиксации окончательного результата, включая истечение срока. Повторная доставка после фиксации результата пропускает SMTP.

Для диагностики сохраняем ID команды и состояние обработки. Код, тело письма и исходная команда остаются вне базы и журналов `NotiService`, включая сообщения об ошибках.

Завершённая запись команды подлежит очистке через 24 часа после окончания срока кода. Noti проверяет срок хранения при старте и затем раз в минуту. После очистки поздняя копия команды завершается без вызова SMTP, потому что обработчик проверяет срок кода из самой команды. [Решение 028](decisions.md#028-срок-хранения-состояния-команд-кодов)

### Информационное письмо о заявке

1. **Согласована схема transactional outbox с отдельным процессом публикации в составе `OrderService`.** Процесс читает ожидающие записи из базы `OrderService` и передаёт события в RabbitMQ. Создание и чтение заявки не ждут публикации. Событие содержит `event_id`, тип и версию схемы, время, ID и номер заказа и подтверждённый email получателя на момент создания. Получатель письма определяется по снимку события. Событие заказа не содержит имени, телефона, адреса объекта, кодов или сессий. `NotiService` формирует письмо по данным события. Ссылку на карточку он строит из настроенного адреса веб-приложения и ID заказа. Письмо сообщает о создании заявки.
2. Для событий заказа в RabbitMQ предлагаются постоянные сообщения, устойчивая очередь и подтверждение издателю. Фоновый процесс отмечает публикацию только после подтверждения маршрутизированного сообщения. При ошибке маршрутизации, недоступности брокера или потере подтверждения запись остаётся доступной для повторной публикации с тем же `event_id`. [Подтверждения RabbitMQ](https://www.rabbitmq.com/docs/confirms) · [Руководство по издателям RabbitMQ](https://www.rabbitmq.com/docs/publishers)
3. Обработчик заказов `NotiService` сохраняет задание с уникальным `event_id` или находит его при повторе. Подтверждает сообщение брокеру после фиксации задания. Если подтверждение потеряно, повторная доставка находит то же задание. Отправку выполняет отдельный процесс в составе сервиса уведомлений. Он продолжает незавершённое задание по сохранённому состоянию, а завершённое пропускает. Для восстановления после падения можно использовать временный захват задания с истечением срока. При временной ошибке SMTP сохраняется попытка и назначается повтор этого задания. [Надёжность доставки RabbitMQ](https://www.rabbitmq.com/docs/reliability)
4. Гарантируем одно сохранённое задание на событие. Если SMTP принял письмо, но сервис потерял подтверждение или завершился до записи успеха, повтор отправки может дать второе письмо. Это отдельный сбой доставки, который не создаёт второй заказ или второе задание.

### SMTP: локальное окружение и реальная доставка

**Согласовано разделение режимов.** Для реальной доставки `NotiService` использует TLS с проверкой цепочки сертификата и имени SMTP-сервера и учётные данные почтового провайдера. При ошибке TLS отправка не продолжается через незащищённое соединение; учётные данные также не передаются без проверенного TLS. Конкретный провайдер, порт и вариант TLS (сразу при соединении или обязательный STARTTLS) ещё выбираются. Секреты не включаются в репозиторий, образ контейнера или журналы.

Локальный Mailpit принимает тестовые письма по SMTP без TLS и аутентификации внутри отдельной сети Docker. SMTP-порт остаётся внутренним, внешняя пересылка в Mailpit отключена. Реальная доставка требует отдельной конфигурации с проверкой TLS и учётными данными провайдера. [Настройка SMTP Mailpit](https://mailpit.axllent.org/docs/configuration/smtp/)

## Предлагаемое окружение Docker Compose

Четыре приложения, три PostgreSQL с отдельными томами и доступами, RabbitMQ, выбранный внутренний CA `step-ca` и Mailpit. Хранение состояния и запуск `step-ca` уточняются при проектировании его жизненного цикла. Web API обращается к своему Envoy-sidecar через изолированный Unix-сокет. Этот Envoy устанавливает mTLS-соединения с отдельными Envoy-sidecar `OrderService` и `AuthService`. Каждый входящий Envoy передаёт запросы в свой FastAPI через выделенный Unix-сокет. Публикатор использует образ `OrderService` и его БД. Обработчики кодов и заказов используют образ `NotiService` и работают независимо. Процессы можно запускать отдельными контейнерами из тех же образов.

На машине разработчика публикуем только входящий HTTPS Envoy Web на `127.0.0.1:8443`. Через него доступны веб-приложение и интерфейс Mailpit. API и БД остаются во внутренних сетях. У каждой БД своя сеть с её владельцем. RabbitMQ доступен `AuthService`, публикатору `OrderService` и обработчикам `NotiService`. SMTP Mailpit доступен обработчикам `NotiService`. Миграции запускаются отдельно для каждой базы после проверки её готовности. Готовность `OrderService` зависит от его БД и миграций. Публикатор переподключается к брокеру самостоятельно, чтобы его остановка не мешала созданию и чтению заявок. [Сети Docker Compose](https://docs.docker.com/compose/how-tos/networking/) · [Порядок запуска Compose](https://docs.docker.com/compose/how-tos/startup-order/) · [Mailpit в Docker](https://mailpit.axllent.org/docs/install/docker/)

### Локальный HTTPS для браузера

Web открывается по `https://app.ceilings.test:8443`, интерфейс Mailpit — по `https://mailpit.ceilings.test:8443`. В `hosts` на машине разработчика оба имени указывают на `127.0.0.1`. Один входящий listener Envoy Web принимает HTTPS и маршрутизирует запросы по точному имени хоста. `app.ceilings.test` обслуживает Web через отдельный входящий Unix-сокет, `mailpit.ceilings.test` — внутренний HTTP-интерфейс Mailpit. Исходящий listener Envoy Web для Auth и Order доступен через свой Unix-сокет. SMTP Mailpit остаётся во внутренней сети Compose. [Публикация портов Docker](https://docs.docker.com/engine/network/port-publishing/)

Для браузерного HTTPS разработчик выполняет `mkcert -install` на своей машине и выпускает один сертификат для `app.ceilings.test` и `mailpit.ceilings.test`. Envoy Web получает серверный сертификат и соответствующий закрытый ключ из файлов вне репозитория. Закрытый ключ CA `mkcert` остаётся на машине разработчика. Для внутреннего mTLS продолжаем использовать сертификаты `step-ca`. [Документация mkcert](https://github.com/FiloSottile/mkcert) · [Решение 031](decisions.md#031-локальный-https-для-web-и-mailpit)

Web устанавливает cookie своего хоста с `Secure` и без атрибута `Domain`. Браузер отправляет их только на `app.ceilings.test`. Раздельные имена позволяют проверить это даже при одинаковом HTTPS-порте. [Правила отправки cookie](https://www.rfc-editor.org/rfc/rfc6265.html#section-5.4)

## Подключения к PostgreSQL и RabbitMQ

Приложения подключаются напрямую по TLS. Клиент проверяет цепочку доверия и имя сервера по сертификату. Для внутренних серверных сертификатов используем `step-ca`. PostgreSQL и RabbitMQ проверяют отдельные учётные данные своего клиента и применяют права его роли. Порты PostgreSQL и AMQP остаются во внутренних сетях Compose. [Решение 026](decisions.md#026-tls-и-права-подключений-к-postgresql-и-rabbitmq)

### PostgreSQL

У каждого экземпляра PostgreSQL своя сеть. `AuthService` подключается к базе доступа, API и публикатор `OrderService` — к базе заказов, обработчики `NotiService` — к базе уведомлений. Web API пользуется HTTP API сервисов. Сертификат каждой БД выдаётся на имя, по которому клиент подключается внутри Compose.

В приложении драйвер PostgreSQL использует `sslmode=verify-full`. Сервер разрешает сетевые подключения по правилам `hostssl` в `pg_hba.conf` с аутентификацией `scram-sha-256`. Соединение без TLS отклоняется. Рабочие роли получают права для операций с данными своего сервиса. Изменения схемы выполняет отдельная роль миграций каждой базы. [Проверка сервера PostgreSQL](https://www.postgresql.org/docs/current/preventing-server-spoofing.html) · [Правила клиентской аутентификации](https://www.postgresql.org/docs/current/auth-pg-hba-conf.html)

### RabbitMQ

Один брокер принимает AMQP поверх TLS. Клиенты проверяют цепочку и имя брокера. Для каждой из двух очередей есть свой именованный обменник. При развёртывании создаём очереди, обменники и привязки. Рабочие учётные записи получают следующие права. [TLS в RabbitMQ](https://www.rabbitmq.com/docs/ssl) · [Права доступа в RabbitMQ](https://www.rabbitmq.com/docs/access-control#authorisation-how-permissions-work)

| Процесс | Разрешение |
|---|---|
| `AuthService` | `write` на обменник команд отправки кодов |
| Публикатор `OrderService` | `write` на обменник событий заказов |
| Обработчик кодов `NotiService` | `read` на очередь кодов |
| Обработчик заказов `NotiService` | `read` на очередь событий заказов |

Право `configure` на ресурсы обоих потоков остаётся у учётной записи развёртывания. Обработчики используют разные логины и пароли, поэтому учётная запись обработчика заказов не даёт доступа к очереди кодов.

### Сертификаты и секреты в Compose

Оператор получает через `step-ca` отдельный серверный сертификат на DNS-имя каждого из трёх PostgreSQL и RabbitMQ. Для замены он заранее готовит новый комплект и проверяет имя и соответствие сертификата ключу. В локальном Compose оператор перезапускает только соответствующий PostgreSQL или RabbitMQ с новым комплектом, сохраняя его том данных. Соединения к этому серверу прерываются на время перезапуска, затем клиенты подключаются снова и проверяют сертификат.

Пароли PostgreSQL, RabbitMQ, SMTP и закрытый ключ подписи JWT храним в файлах вне репозитория. Compose secrets монтирует каждый файл только нужным контейнерам в `/run/secrets`. Открытый JWKS и корневой сертификат CA передаются нужным сервисам как конфигурация только для чтения. [Секреты в Docker Compose](https://docs.docker.com/compose/how-tos/use-secrets/) · [Решение 029](decisions.md#029-сертификаты-и-секреты-в-compose)

## Приёмка первой заявки

Локальный HTTPS проверяем в первой задаче этапа 2. Сквозные прогоны с созданием и чтением заявки выполняем после того, как работают оба действия и есть сессии клиента и админа. В том числе это относится к отключению `AuthService`, восстановлению связи после истечения сертификата или CRL и восстановлению публикации после сбоя RabbitMQ.

| Прогон | Проверяемый исход |
|---|---|
| Локальный HTTPS и изоляция cookie | По инструкции на чистом окружении настраиваем имена в `hosts`, доверие к локальному CA и запускаем Compose. Открываем оба HTTPS-адреса в обычном браузере без предупреждений о сертификате. Web выдаёт тестовую `Secure` cookie без `Domain`. В DevTools проверяем, что браузер сохранил её и отправляет на Web, а в запросе к Mailpit этой cookie нет. |
| Маршрутизация локального HTTPS | Запрос к `https://app.ceilings.test:8443` попадает в Web, запрос к `https://mailpit.ceilings.test:8443` — в Mailpit. Отдельно через успешно установленное TLS-соединение проверяем HTTP-запрос с неизвестным именем в `Host` или `:authority`: Envoy отклоняет его, запрос не попадает ни в Web, ни в Mailpit. |
| Вход и заявка | Код подтверждает email, заказ создаёт только отдельная отправка. Клиент видит свою заявку, админ видит её в панели, в Mailpit появляется информационное письмо. Клиент не читает чужую заявку и не открывает панель. |
| Одновременные отправки с одинаковым ID | Один заказ, одно событие истории и одна запись публикации. Обе отправки с одинаковыми данными получают один ID заказа. Повтор того же ID с изменёнными полями получает конфликт. |
| Одновременные отправки с разными ID | Один активный заказ. Проигравший запрос получает конфликт со ссылкой на него. |
| Ответ потерялся после фиксации | Повтор той же отправки открывает прежнюю заявку. Остаются один заказ, одно событие истории и одна запись публикации. После доставки события создаётся одно задание на письмо. |
| Остановка и восстановление RabbitMQ | Заранее получаем действующие сессии клиента и админа, затем останавливаем RabbitMQ и создаём заявку. Клиент видит её в кабинете, админ — в панели. В БД сохранены один заказ, одно событие истории и ожидающая запись публикации. Восстанавливаем RabbitMQ. Публикатор сам отправляет ожидающее событие, `NotiService` создаёт задание, письмо появляется в Mailpit. Дожидаемся письма перед повторной доставкой того же `event_id`. После повтора остаётся одно задание на письмо, завершённое задание пропускается. |
| Очередь писем о заказах задержана | Останавливаем обработчик заказов или создаём очередь необработанных писем о заказах. Запрашиваем код и получаем его в Mailpit до возобновления обработки заказов. |
| Код истёк во время сбоя брокера | Останавливаем обработчик кодов, проверяем, что RabbitMQ принял команду, и прерываем доступ к брокеру до истечения срока кода. Восстанавливаем доступ с сохранённой очередью и запускаем обработчик. По ID команды проверяем, что он отбросил её как просроченную. Вызова SMTP и письма в Mailpit нет. Новый запрос после восстановления даёт свежий код. |
| Потеря подтверждения публикации кода | RabbitMQ принимает команду, но подтверждение не доходит до `AuthService`. Ретраи сохраняют ID, код и срок. Если подтверждение так и не получено, интерфейс показывает предупреждение и позволяет ввести действующий код из всё же пришедшего письма. |
| Брокер недоступен при запросе кода | До трёх попыток укладываются в 4 секунды публикации, с паузами 250 и 750 мс перед повторами в пределах бюджета. Интерфейс показывает предупреждение, поле ввода остаётся открытым. Новый запрос доступен в пределах лимитов. |
| Повтор команды кода | Доставляем одну команду одновременно и повторно после перезапуска. PostgreSQL сохраняет одну запись на `command_id`, в каждый момент только один обработчик начинает попытку. Повтор завершённой команды не вызывает SMTP. |
| Очистка состояний команд кодов | Проверяем повтор завершённой команды, пока запись хранится. Через 24 часа после истечения кода удаляем запись и повторяем доставку того же `command_id`. В обоих случаях повтора отправки в SMTP нет. После очистки решение принимается по сроку кода из команды. |
| Выдача, лимиты и одноразовость кода | Для клиента и админа проверяем границу 10 минут, отказ после пятого неверного ввода и один успешный вход при двух одновременных вводах верного кода. Запрос до истечения минуты и шестой выпуск за скользящий час отклоняются, текущий код остаётся действующим до своего срока. Выпуск с потерянным подтверждением засчитывается. |
| Временный отказ SMTP при отправке кода | SMTP явно отклоняет отправку. `NotiService` сохраняет отказ и выполняет одну повторную попытку через 5 секунд. Перезапуск после сохранения отказа сохраняет срок и число попыток. Если код успел истечь, повторного вызова SMTP нет. |
| Неизвестный результат SMTP при отправке кода | Теряем ответ после принятия письма SMTP. Отдельно останавливаем процесс после начала отправки и до сохранения её результата. После повтора команды или перезапуска остаётся один `command_id` со статусом «Исход неизвестен». Автоматического повторного вызова SMTP нет. Из пришедшего письма можно ввести действующий код. |
| Новый запрос отменяет предыдущий код | Запрашиваем код A, задерживаем его письмо, затем выпускаем код B для того же email и назначения входа. Доставляем письмо A после письма B до истечения обоих кодов. Отправка A допустима, но вход по A отклоняется, а по действующему B разрешён. Технический ретрай команды B не отменяет B и не создаёт нового кода. |
| Диагностика отправки кода | При успешной отправке, ошибке SMTP и истечении срока в базе и журналах есть состояние обработки по `command_id`. Код, тело письма и исходная команда в них отсутствуют. |
| Событие доставлено повторно | Имитируем потерю подтверждения после сохранения задания, но до отправки письма. Повтор находит задание по `event_id` и его обработка продолжается. После завершения ещё один повтор не создаёт задание или попытку. |
| Временный сбой SMTP | Заказ остаётся доступным, сервис уведомлений сохраняет ошибку попытки и повторяет доставку по тому же заданию. |
| Чужой заказ и подмена владельца | Клиент с корректным JWT запрашивает чужую карточку и подставляет чужой ID пользователя в форму или заголовки. Данные чужого заказа не возвращаются. Карточка читается одним запросом с условием владельца из доверенного контекста; списки и история также ограничены владельцем. |
| Unix-сокет и БД OrderService | Через пару Envoy запрос достигает FastAPI по Unix-сокету и успешно создаёт/читает заказ в PostgreSQL. Прямое сетевое обращение к FastAPI недоступно, в том числе со стороны сети БД. После перезапуска FastAPI соединение через сокет восстанавливается. |
| Web → Auth через Envoy | Вход клиента и админа по коду и обновление токенов проходят через Web и Auth Envoy. Envoy Auth отклоняет соединения без клиентского сертификата или с действительным сертификатом другого сервиса от того же CA. Envoy Web отклоняет сертификат Auth с неверным DNS SAN даже при доверенной цепочке. |
| Изоляция FastAPI Auth | Прямой сетевой вход в FastAPI Auth недоступен, в том числе из сети его PostgreSQL. Посторонние контейнеры не могут подключиться к Unix-сокету Auth или вызвать Auth от имени Web через исходящий Envoy. Через штатный маршрут Auth сохраняет подключение к своей БД. |
| Недоступен канал Web → Auth | Останавливаем Envoy Auth, оставляя AuthService и маршрут Web → Order доступными. Подача заявки, обновление токенов и защищённый запрос админа отклоняются. Клиент с действующим JWT читает свой заказ. После запуска Envoy Auth маршрут восстанавливается. |
| Отзыв сертификатов на Web → Auth | Отдельно отзываем сертификат Auth и общий клиентский сертификат Web. После закрытия соединений и загрузки свежего CRL ещё действующий отозванный сертификат отклоняется, а новый проходит. При отзыве сертификата Web проверяем отклонение на обоих маршрутах. |
| TLS и роли PostgreSQL | Каждый сервис работает со своей БД, а роль миграций может менять её схему. PostgreSQL отклоняет подключения без TLS. Клиент отклоняет серверный сертификат от недоверенного CA или с неверным именем. Рабочая роль не может менять схему или подключиться к чужой БД. |
| TLS и права RabbitMQ | Публикация и потребление в каждом потоке работают. RabbitMQ отклоняет подключения без TLS. Клиент отклоняет серверный сертификат от недоверенного CA или с неверным именем. Публикатор не может писать в чужой обменник. Обработчик не может читать чужую очередь. Рабочие учётные записи не могут создавать или менять очереди и привязки. |
| Замена сертификатов PostgreSQL и RabbitMQ | Для каждого сервера готовим проверенный комплект и перезапускаем только этот сервер. Клиенты переподключаются, видят новый сертификат и выполняют штатную операцию. Записи PostgreSQL и постоянное тестовое сообщение в устойчивой очереди RabbitMQ сохраняются. |
| Передача секретов в Compose | Контейнеры получают только назначенные им файлы в `/run/secrets`. Web получает открытый JWKS для чтения. Закрытый ключ JWT доступен в `AuthService`. Проверяем отсутствие паролей и закрытого ключа в файлах репозитория и образах. |
| Срок сервисного сертификата и постоянное хранение | Проверяем, что выданный сертификат Envoy действует 24 часа. Пересоздаём Envoy и убеждаемся, что действующие ключ и сертификат сохранились. |
| Изоляция процессов обновления | Каждый процесс обновляет сертификат своего Envoy через `step-ca`. Проверяем, что он не может прочитать или заменить файлы ключей и сертификатов двух остальных Envoy. Остановка одного процесса не останавливает остальные. |
| Назначения сервисных сертификатов | Проверяем, что сертификат Web содержит только `clientAuth`, а сертификаты Order и Auth — `serverAuth` и `clientAuth`. Web устанавливает mTLS-соединения с Order и Auth, а каждый процесс обновления проходит клиентскую аутентификацию в `step-ca` с сертификатом своего Envoy. |
| Срок корневого CRL и истечение локальной копии | На сокращённых сроках проверяем, что действующий подписанный пустой корневой CRL допускает валидную цепочку. Проверяем плановую замену до истечения. Если корневой CRL истекает, Envoy отклоняет новые соединения даже при действующем сервисном CRL. После загрузки свежего корневого списка соединения снова проходят. |
| Срок сервисного CRL и истечение локальной копии | При недоступном `step-ca` новые соединения работают по действующей локальной копии. После `nextUpdate` новые соединения, включая попытки возобновления TLS, отклоняются. Оператор вручную загружает действующий список, и соединения снова устанавливаются. Списки с неверной подписью или истёкшим сроком не публикуются как обновление. |
| Восстановление связи с сохранённой заявкой | Создаём заявку в локальном Compose. На сокращённых сроках отдельно воспроизводим истечение сервисного сертификата и истечение CRL. Новое соединение отклоняется. Оператор по инструкции получает новый сертификат или загружает свежий CRL. После каждого восстановления клиент и админ открывают ту же заявку с прежним ID и историей. Тома PostgreSQL сохраняются. |
| Сертификат истёк до восстановления CA | После истечения проверяем отказ нового полного TLS-рукопожатия. Возвращаем CA и проверяем, что просроченный сертификат не обновляется. Оператор повторяет первую выдачу. После установки нового сертификата новое mTLS-соединение проходит. |
| Плановое обновление сертификата и ключа через SDS | Для каждого прокси обновляем сертификат через `rekey` и публикуем новый сертификат вместе с соответствующим ключом. Проверяем, что Envoy продолжает работать и установленное mTLS-соединение сохраняется. На новом полном TLS-рукопожатии проверяем новый серийный номер сертификата и новый открытый ключ. Прерываем процесс после записи одного файла нового комплекта, до замены `tls-sds.yaml`. Envoy продолжает предъявлять прежний сертификат. После успешной публикации целого комплекта повторяем проверку нового соединения без перезапуска. |
| Первоначальная выдача сертификата | Оператор разрешает имя Web для конкретного запроса на сертификат. `step-ca` подписывает разрешённый запрос, Envoy Web устанавливает mTLS-соединение. Запрос без токена отклоняется. Отдельно проверяем отклонение при несовпадении имени в SAN, подмене запроса при том же имени, истёкшем токене и повторном предъявлении использованного токена. |
| Изоляция исходящего Envoy Web | Web API обращается к своему Envoy через Unix-сокет и успешно вызывает Order и Auth. Посторонний контейнер не имеет доступа к тому сокету и не может вызвать исходящий прокси по TCP, чтобы использовать сертификат Web. Тома сокетов Web и Order различаются. После перезапуска прокси разрешённое соединение восстанавливается. |
| Проверка JWT | Поддельная подпись, истёкший срок, неверный издатель или получатель не допускают защищённый запрос к `OrderService`. Серверная сессия сама по себе не делает такой access token допустимым. |
| Плановая смена ключа JWT | Web загружает оба открытых ключа до переключения подписи. Токен со старой подписью проходит до своего `exp`, новый токен проходит сразу. Через 10 минут после последней подписи старый открытый ключ удаляется. Проверка подписи работает локально. Сроки серверных сессий сохраняются. |
| Аварийная замена ключа JWT | После удаления скомпрометированного ключа из JWKS и загрузки набора Web отклоняет ещё не истёкший JWT со старым `kid`. Действующая сессия и refresh token позволяют получить JWT с новым `kid`. |
| Недоступен AuthService | С действительным локально проверенным JWT клиент читает свой заказ без запроса в `AuthService`. Подача заявки, остальные операции с обязательной актуальной проверкой и все защищённые запросы админа, включая чтение, не разрешаются. Обновление токенов при недоступном `AuthService` невозможно. |
| Отзыв прав админа | На двух устройствах сохраняем ещё не истёкшие JWT, отзываем права и проверяем отказ на следующем защищённом запросе с каждого устройства, включая чтение. При смене email той же записи прежние коды и сессии недействительны, доступ и обновление токенов через них не разрешаются; авторство в истории сохраняется. |
| Подтверждённый выход, блокировка и отзыв клиентской сессии | После серверного отзыва обновление и подача заявки отклоняются сразу. При подтверждённом выходе Web API очищает обе cookie. Отдельно проверяем, что запоздалое обновление не возвращает браузер в кабинет. Ранее выданный JWT допускает обычное клиентское чтение до `exp` и в пределах 5 минут после прекращения сессии. На момент `exp` чтение по нему отклоняется. |
| Выход при недоступном Auth или потере ответа | При недоступном Auth браузер сохраняет cookie, показывает ошибку и позволяет повторить выход. Отдельно теряем ответ после успешного отзыва. После восстановления связи повтор подтверждает отзыв той же сессии и Web очищает cookie. Другие сессии сохраняются. |
| Две вкладки в браузере | В браузере с общей блокировкой вкладок обе вкладки одновременно нуждаются в обновлении. Одна обновляет токены, вторая после ожидания продолжает с новыми cookie. До Auth доходит один запрос на обновление. |
| Потеря ответа на обновление | Проверяем три случая: браузер применил новые cookie и продолжает работу. Auth не зафиксировал обмен и `R0` ещё можно использовать. Auth зафиксировал обмен, браузер остался с `R0`, его повтор отзывает сессию и требуется новый email-код. |
| Повторное предъявление refresh token | При двух запросах с `R0` первый обмен проходит, второе предъявление отзывает только эту сессию. `R1` больше не позволяет обновить токены, а другие устройства сохраняют доступ. Неизвестный токен не меняет состояние сессий. |
| Повторный вход после потери ответа на заявку | Создаём заявку и теряем ответ на отправку. При следующем обновлении токенов теряем ответ после фиксации обмена, повтор старого токена отзывает сессию. После входа в ту же учётную запись сохраняются поля и ID исходной отправки. Когда клиент повторяет отправку, открывается прежний заказ. Остаются один заказ, одно событие истории, одна запись публикации и одно задание на письмо после доставки события. При входе в другую запись прежняя форма не открывается. |
| Абсолютный срок сессии | Обновляем токены за минуту до конца сессии клиента и админа. JWT действует максимум оставшуюся минуту. На границе сессии обновление и доступ по выданной паре прекращаются. |
| Cookie и проверка Origin | Браузер принимает обе cookie с согласованными атрибутами. После перезагрузки с истёкшим JWT и действующим refresh token обновление с точным `Origin` работает. Запросы с чужим, отсутствующим или `null` Origin отклоняются до изменения состояния. Проверяем запрос и подтверждение кода, обновление, выход и подачу заявки. Для локального профиля отдельно проверяем Origin Mailpit. |

## Инфраструктурная приёмка выпуска

| Прогон | Проверяемый исход |
|---|---|
| Автоматическое обновление сертификатов | Первая попытка запланирована за 8 часов до истечения. При недоступном `step-ca` процесс журналирует причину, повторяет запрос каждые 5 минут и предупреждает оператора за час до истечения, если обновление ещё не удалось. При восстановлении CA до истечения процесс получает и применяет новый комплект через SDS без вмешательства оператора. |
| Автоматическая доставка сервисного CRL | `step-ca` перевыпускает список каждые 8 часов и при отзыве. Процессы проверяют список раз в минуту и применяют его через SDS. Если за час до истечения свежего списка ещё нет, оператор получает предупреждение. Принудительная загрузка при отзыве работает до следующей плановой проверки. |
| Хранение и восстановление CA | Имитируем потерю сервисного ключа и повторяем первую выдачу с новой парой. Отдельно проверяем восстановление `step-ca` и сохранность отзывов по согласованной процедуре восстановления. |
| Плановая замена ключей CA | На сокращённых тестовых сроках проверяем оба перехода. При смене промежуточного CA старые действующие сертификаты продолжают работать, а штатное обновление переводит Envoy на новую цепочку. При смене корневого CA проверяем mTLS и обновление во время перехода и после удаления старого корня. Сертификаты под старым корнем после его удаления отклоняются. |
| Активный отзыв сервисных сертификатов | В тестовом окружении отзываем несколько ещё действующих сертификатов одного сервисного ключа. `step-ca` отклоняет их обновление, остановка проверяющего Envoy закрывает действующее соединение. После запуска с новым CRL отозванные сертификаты отклоняются на полном рукопожатии. Новый ключ и сертификат того же сервиса восстанавливают доступ. |
| Компрометация промежуточного или корневого CA | Проверяем каждый случай отдельно по согласованной процедуре. Участники отклоняют прежнюю цепочку при mTLS и при обновлении сертификатов. Старые соединения закрыты, новая цепочка позволяет установить соединение и штатно обновлять сертификаты. |
| Реальный SMTP | Если выпуск включает реальную доставку, проверяем соединение с корректным сертификатом и учётными данными. При недоверенном или просроченном сертификате, неверном имени или невозможности обязательного TLS отправка останавливается без передачи секретов и письма в открытом виде. Для прогона подходит управляемый тестовый SMTP-сервер. |
