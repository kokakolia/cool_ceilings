# Юз-кейсы

Актуально на 24 ноября 2026 года. Правила продукта находятся в [product.md](product.md). UC-02, основная схема клиентского входа, UC-05, UC-07, основные пути UC-08–UC-10, UC-11 и UC-12 согласованы для этапа до проектирования. В UC-06 остались отмеченные вопросы; остальные сценарии — черновики. Основные правила UC-15 согласованы. UC-01, UC-13 и UC-16 отложены до следующих версий. Правила отзывов сохранены для будущего выпуска. Точные поля и исключения из черновиков не считаются автоматически утверждёнными.

## UC-01. Получить предварительный расчёт — отложенный черновик

**Участник:** посетитель или клиент. **Условие:** известны параметры для учебной формулы.

**Сценарий:** открывает калькулятор, вводит параметры; сервер рассчитывает ориентир, интерфейс показывает предварительный характер цены и возможность перейти к заявке.

**Результат:** расчёт получен, учётная запись и заказ не создаются.

**Альтернативы:** параметры неизвестны — переход к заявке без расчёта; ошибки ввода — исправление; пустые поля не означают нулевые значения. Формула и обязательные поля пока не выбраны.

## UC-02. Подтвердить почту и отправить первую заявку — согласованный основной путь

**Участник.** Посетитель или клиент без предыдущих заявок. **Цель.** Подать первую заявку со страницы личного кабинета.

1. Посетитель открывает страницу «Личный кабинет» напрямую. Без действующей сессии доступна только форма с полем email и кнопкой «Получить код».
2. После нажатия «Получить код» система проверяет формат email и ограничения частоты отправки, затем передаёт команду отправки письма через RabbitMQ в `NotiService`. При временном сбое публикации выполняются ограниченные ретраи с тем же ID команды, кодом и сроком; `NotiService` распознаёт повторы по ID. Ниже появляется поле кода и возможность исправить email или запросить новый код. До подтверждения существует только временный запрос.
3. Посетитель вводит или вставляет код. Полный код проверяется автоматически. Доступный способ явной отправки уточняется при проектировании интерфейса.
4. Правильный код открывает существующую учётную запись или создаёт подтверждённую запись для нового email. Начинается 30-дневная сессия на устройстве. При действующей сессии клиент сразу переходит к следующему шагу.
5. Если заявок ещё не было, на той же странице сразу открывается форма первой заявки. Это относится и к клиенту, который ранее подтвердил email, но так и не подал заявку. При наличии заказов кабинет открывается по UC-03.
6. Клиент вводит имя, российский мобильный или городской телефон с `+7` или `8` и полный адрес объекта одним полем. Адрес включает населённый пункт, улицу и дом, при наличии — корпус или строение. Квартиру, подъезд и домофон можно уточнить при согласовании визита. Подтверждённый email подставляется из учётной записи. Параметры помещения, пожелания и комментарий необязательны.
7. Клиент нажимает «Подать заявку». Web API локально проверяет JWT и дополнительно проверяет актуальные сессию и права через сервис доступа и передаёт в `OrderService` поля формы, идентификатор отправки, подтверждённые ID, роль и email. `OrderService` проверяет право на действие, поля и отсутствие другого активного заказа. Он сохраняет заявку, событие создания и запись для публикации одной транзакцией. Имя и телефон сохраняются как контакты для этого обращения.
8. После сохранения клиент видит свою заявку, админ видит её в панели. Сервис уведомлений получает событие через брокер и отправляет информационное письмо по UC-15.

**Результат.** У подтверждённого клиента один новый активный заказ. Компания рассматривает заявку отдельно по UC-05. Если клиент ушёл после подтверждения кода, учётная запись сохраняется. Заказ создаётся при отправке формы.

**Краевые случаи:**

| Случай | Результат |
|---|---|
| Неверный, истёкший или использованный код | Код из 6 цифр действует 10 минут с выпуска и используется один раз. После пяти неверных вводов нужен новый код. При одновременном вводе верного кода только один запрос открывает сессию |
| Сработал лимит запроса кода | Для email и назначения входа разрешён максимум один выпуск в минуту и пять за скользящий час. Отклонённый запрос сохраняет текущий код. Выпуск с потерянным подтверждением учитывается в лимите |
| Новый запрос кода | Выпуск нового кода отменяет предыдущий для того же email и назначения входа. Старое письмо может прийти даже после нового, но старый код не открывает кабинет. Технический ретрай той же команды действующий код не отменяет |
| Отправку не удалось подтвердить | Если `AuthService` не получил подтверждение от RabbitMQ после попыток публикации, показываем предупреждение. Поле ввода остаётся доступным. Код из всё же пришедшего письма можно использовать до его истечения. Если письма нет, доступен новый запрос в пределах лимитов |
| Email уже существует | Код выполняет вход в прежнюю запись, без дубля |
| Опечатка до подтверждения | Исправить адрес в блоке, запросить код для нового адреса; старый запрос не подтверждает новый адрес |
| Страница закрыта до подтверждения | Открыть заново и запросить код; постоянной неподтверждённой записи нет |
| Вторая заявка из старой вкладки | Пока первый заказ активен, новая заявка не создаётся. Клиенту предлагают открыть активный заказ |
| Сессия истекла или отозвана в открытой форме | Показать форму email на той же странице. После входа в ту же учётную запись вернуть поля заявки и идентификатор уже начатой отправки. Клиент отправляет её сам. Другая учётная запись не получает эти поля и идентификатор |
| Заказ сохранён, ответ потерялся | Повтор с тем же идентификатором и теми же полями открывает созданную заявку. Остаются один заказ, одно событие создания, одна запись публикации и одно задание после доставки события |
| Тот же идентификатор, другие поля | Ошибка конфликта. Сохранённая заявка остаётся прежней |
| Две одновременные отправки | При одинаковом идентификаторе и полях обе получают один заказ. При разных идентификаторах создаётся один активный заказ, второй запрос получает конфликт со ссылкой на него |

**Приёмка.** При открытии страницы без сессии доступна только форма email и запроса кода. Поле кода появляется после запроса, а форма первой заявки открывается только при отсутствии предыдущих заявок и наличии действующей сессии. Подтверждение кода само по себе не отправляет заявку. Сервер требует подтверждённый email, имя, российский телефон с `+7` или `8` и полный адрес объекта. Форма принимает пробелы, скобки и дефисы в телефоне, отклоняет иностранные номера и даёт ввести адрес без отдельного выбора города. `OrderService` проверяет отсутствие другого активного заказа и сохраняет одно событие и одну запись публикации. Сервис уведомлений создаёт одно задание на письмо на событие. Сохранение черновика после полного закрытия страницы не согласовано. Сроки кодов и ограничения запросов уточняются при проектировании.

## UC-03. Открыть личный кабинет и просмотреть свои заказы — основная схема согласована

**Участник.** Посетитель или клиент, открывающий страницу «Личный кабинет».

**Сценарий.** При действующей сессии кабинет открывается сразу. Иначе посетитель видит только форму email с кнопкой «Получить код». После запроса вводит код в появившемся ниже поле. Правильный код открывает существующую запись либо создаёт подтверждённую запись для нового email.

- Есть активный заказ — кабинет открывает его, история предыдущих заказов доступна по UC-12.
- Все прежние заказы закрыты — кабинет показывает историю и кнопку «Оставить заявку» по UC-04.
- Заявок ещё не было — кабинет сразу открывает форму первой заявки по UC-02, включая повторный визит после подтверждения email без отправки заявки.

**Результат.** Клиент видит только свои данные. Серверная сессия действует не более 30 дней с подтверждения кода на устройстве. Обновление токенов сохраняет её исходный срок. Учётная запись сохраняется после выхода или отзыва сессии. После выхода, блокировки или отзыва обновление токенов и подача заявки прекращаются сразу. Ранее выданный JWT позволяет читать свои заказы до истечения токена, максимум ещё 5 минут.

**Краевые случаи.** Чужой заказ недоступен. Неверный код не открывает кабинет. Истёкший access token не допускает чтение; обновление через `AuthService` возможно только в рамках допустимого refresh token и действующей серверной сессии. Когда продолжить вход невозможно, на той же странице снова появляется форма email.

**Выход и восстановление доступа.** После перезагрузки страницы с истёкшим JWT браузер может продолжить действующую сессию с помощью refresh token. Запрос на обновление, как и другие изменяющие браузерные запросы, проходит только с точным `Origin` Web из конфигурации. При выборе «Выйти» Web очищает cookie и показывает форму входа после подтверждения отзыва от `AuthService`. Если подтвердить отзыв не удалось, показывается ошибка, cookie сохраняются для повтора. Повтор завершает выход, если Auth уже отозвал ту же сессию. Эти правила действуют и в панели админа. [Проверки обновления и выхода](first-scenario-design.md#приёмка-первой-заявки)

**Приёмка доступа и чтения.** Web API локально проверяет подпись JWT, срок, издателя и получателя. Обычное чтение своего заказа с допустимым JWT работает и при недоступном `AuthService`. `OrderService` проверяет владельца по доверенному контексту при чтении карточки. Подстановка чужого ID заказа или пользователя не открывает чужие данные. Списки и история также ограничены владельцем. После выхода, блокировки или отзыва проверяем отказ в обновлении и подаче заявки и границу чтения на момент истечения JWT. В штатном случае две вкладки продолжают работу после одного обновления. Потеря ответа сама по себе не завершает вход. Повторное предъявление использованного refresh token отзывает только связанную с ним сессию, после чего нужен новый вход по коду. Обновление сохраняет исходный абсолютный срок сессии. [Подробные прогоны ротации](first-scenario-design.md#приёмка-первой-заявки)

## UC-04. Создать следующий заказ — черновик

**Участник.** Клиент с действующей сессией. **Условие.** Есть предыдущие заказы и все они закрыты.

**Сценарий.** Клиент нажимает «Оставить заявку» в кабинете. Форма предлагает имя и телефон из последней поданной заявки. Клиент может изменить их и вводит адрес объекта. Email берётся из учётной записи. Для обязательных полей, проверки активного заказа и обработки отправки действуют правила UC-02.

**Результат:** новый заказ активен, предыдущие остаются в истории. **Альтернативы:** активный заказ уже есть — переход к нему; одновременные формы или повтор — без дублей.

## UC-05. Рассмотреть заявку — согласован

**Участник.** Админ, который вошёл в панель под своей персональной записью. **Условие.** Заказ находится в состоянии новой заявки или очереди и принадлежит клиенту с подтверждённым email.

Первую запись с ролью «Админ» создаёт человек, который разворачивает приложение. Он запускает служебную команду после настройки базы и до приёма заявок. Админ входит в панель по отдельному одноразовому email-коду. Для этого назначения действуют те же срок и лимиты, что и в UC-02. Клиентский вход не выдаёт прав на панель. Сессия админа действует не более 8 часов с подтверждения кода. На разных устройствах могут быть отдельные сессии.

Если админ потерял доступ к почте, оператор проверяет его личность и служебной командой меняет email той же учётной записи. Прежние административные коды и сессии отзываются, авторство действий в истории сохраняется. При отзыве прав все сессии админа теряют доступ к панели при следующем запросе.

1. Админ открывает список и карточку заказа. На каждом защищённом запросе Web API локально проверяет JWT и запрашивает актуальные сессию и права в `AuthService`, включая запросы чтения. При невозможности проверить актуальность запрос не разрешается.
2. Просматривает дату поступления, контакты, адрес и имеющиеся пожелания. Необязательные сведения могут отсутствовать.
3. При необходимости общается с клиентом вне сайта. Сайт не требует подтверждать факт разговора.
4. Выбирает принятие, очередь или отказ.
5. Система проверяет действующую административную сессию, права админа и актуальное состояние заказа. Сохраняет решение и событие истории с указанием конкретного админа и времени. Для решения создаётся одно задание на письмо по UC-15.
6. Клиент видит текущее состояние и опубликованное пояснение. После сохранения решения получает email об одобрении, постановке в очередь или отказе по UC-15.

| Решение | Состояние и результат |
|---|---|
| Принять | «Принята, ожидается замер»; дата может быть ещё не согласована |
| Поставить в очередь | «В очереди»; остаётся активным, второй активный заказ недоступен |
| Отклонить | «Отклонён компанией»; история сохраняется, доступен новый заказ, восстановления нет |

После принятия стороны согласуют бесплатный замер. Принятие само по себе не согласует цену работ и не запускает монтаж. Очередь ручная: затем админ принимает или отклоняет, без номеров, автопродвижения и гарантированного срока. Отказ не удаляет заказ или клиента. Новая заявка и очередь занимают единственное место активного заказа клиента. Старый сценарий удаления неподтверждённой заявки исключён.

**Краевые случаи:** без решения заказ остаётся новым; неизвестная дата не препятствует принятию; если клиент не отвечает, админ сам выбирает дальнейшее решение; устаревшая карточка не перезаписывает отмену клиента или решение, сохранённое админом с другого устройства либо другим админом под своей записью; повтор кнопки не дублирует событие. Отказ компании от уже принятого заказа относится к отдельным правилам отмены.

**Приёмка:** принятие/очередь/отказ доступны из новой заявки, принятие/отказ — из очереди; решение сохраняется после обновления; событие с конкретным автором и временем есть в истории; отказ закрывает заказ, очередь не закрывает; закрытый заказ не возвращается в работу.

**Приёмка доступа.** Одноразовый административный код позволяет открыть сессию в панели. После смены email прежние коды и сессии недействительны, а уже записанные действия сохраняют прежнего автора. После отзыва прав следующий защищённый запрос из открытых сессий этого админа отклоняется на всех устройствах, включая чтение с ещё не истёкшим JWT. Недоступность `AuthService` не позволяет продолжить доступ по старым сведениям токена. Истёкший JWT не допускает запрос, а обновление токенов не продлевает абсолютный срок сессии.

**Согласованные пояснения:** причина отказа обязательна и видна клиенту; при постановке в очередь дополнительное пояснение необязательно. Без него показывается стандартный текст «Заявка рассмотрена. Компания пока не готова начать работы». Без действия админа заявка остаётся новой, автоматически в очередь не переходит. Из очереди админ вручную принимает или отклоняет заявку.

**Граница закрытого сценария:** UC-05 закрыт для этапа до проектирования. Email-уведомления об одобрении, очереди и отказе добавлены по указанию автора. Оформление отмены уже принятого заказа решается отдельно.

## UC-06. Записать договорённость о визите — правила пересмотра согласованы

**Участники.** Админ фиксирует визит, клиент согласует его вне сайта. Замер назначается для принятого заказа. Для монтажа согласованный объём и цена работ визита проверяются по действующей утверждённой смете.

**Основной сценарий**

1. Стороны договариваются вне сайта о работах, дате и интервале прибытия.
2. Админ открывает заказ и выбирает действие записи визита. Адрес берётся из заказа.
3. Указывает дату и интервал, при необходимости добавляет видимую клиенту заметку. При переносе монтажа указывает работы, для которых назначена новая дата.
4. Система проверяет актуальность заказа и допустимость действия, сохраняет договорённость и событие истории. Для сохранённого изменения предусмотрено одно задание на email по UC-15.
5. Клиент видит в карточке актуальные дату, интервал, адрес и сведения о работах визита. При переносе монтажа письмо также указывает работы, для которых назначена новая дата.

**Визит во время пересмотра сметы**

- Существующая дата может остаться, если все работы этого визита по-прежнему однозначно покрыты действующей утверждённой сметой по объёму и цене.
- Админ может перенести визит, если он нужен для такого согласованного объёма. Новую дату и интервал согласуют с клиентом. В карточке и письме указывают, для каких работ назначен визит.
- Если назначение зависело от пересматриваемых условий, админ снимает его. Снятие доступно при подготовке и согласовании новой сметы, даже если новой даты пока нет. Прежняя дата остаётся в истории, клиент видит отсутствие действующего назначения и получает письмо.
- Для визита по работам на новых условиях новую дату согласуют после утверждения сметы. Это правило применяется также при общей цене, из которой невозможно однозначно выделить цену работ визита.
- Перенос и снятие меняют расписание, сохраняя стадию заказа, прежние назначения в истории и историю согласований. Допустимый объём работ при пересмотре определён в UC-10.

**Краевые случаи и приёмка**

- При отсутствии договорённости клиент видит, что дата пока не согласована. Прошедшая дата сама по себе не означает выполненный замер или начатый монтаж.
- При снятии назначения сохраняется сам заказ. Перенос сохраняет прежнее значение в истории. Закрытый заказ не получает новое назначение.
- Устаревшая форма не перезаписывает более свежую договорённость, повтор сохранения не создаёт второй визит или новое задание на то же письмо.
- Обе стороны видят один актуальный визит для указанных работ либо отсутствие назначения. Письмо о переносе содержит работы, дату и интервал. Письмо о снятии сообщает об отсутствии нового назначения.

Формат «дата и интервал» согласован. Часовой пояс, проверки интервалов и пересечений определяются при проектировании. Необязательность заметки и причины переноса и дополнительное подтверждение даты клиентом остаются открытыми деталями.

## UC-07. Внести результаты замера — согласован

**Участник:** админ. **Условие:** заказ принят, не закрыт; бесплатный замер выполнен. Прошедшая дата в календаре сама по себе не доказывает выполнения.

**Цель:** сохранить результаты по помещениям так, чтобы клиент видел измеренные параметры и компания могла подготовить смету.

**Согласованный основной сценарий:**

1. Админ открывает заказ и раздел результатов замера.
2. Добавляет одно или несколько помещений по адресу заказа.
3. Для каждого вводит измеренные параметры, материалы и освещение в выбранном объёме, при необходимости добавляет пояснения. Предварительные сведения клиента могут служить подсказкой, но не считаются измеренными автоматически.
4. Нажимает «Сохранить результаты замера». Система проверяет поля и актуальность состояния заказа.
5. Внесённые результаты сохраняются как данные замера, изменение фиксируется в истории. Отдельного сохранённого черновика и дополнительной кнопки публикации нет: сохранённые результаты сразу видны клиенту.
6. При первой фиксации выполненного замера заказ переходит из ожидания замера к подготовке сметы.
7. Клиент видит параметры по помещениям и пояснения. Одно сохранённое действие, даже с несколькими помещениями и сменой статуса, создаёт одно задание на письмо по UC-15.

**Согласованный минимальный состав:** название помещения и измеренная площадь в м² обязательны. Периметр в метрах, количество углов, количество точек освещения, материал или фактура и пояснение необязательны. Это учебная модель, а не подтверждённый профессиональный стандарт замера. Точные числовые пределы и форматы уточняются при проектировании, обязательность перечисленных полей согласована.

**Результат:** опубликованные результаты доступны клиенту, заказ ожидает подготовки сметы. Цена и готовая смета автоматически не возникают только из факта сохранения замеров.

**Альтернативы и крайние случаи:**

- Замер сорвался или пока не закончен — не отмечать его выполненным автоматически; админ продолжает внешнее согласование или запись визита по UC-06.
- Несколько помещений — один заказ с отдельными записями помещений, не отдельные заказы для каждой комнаты.
- Некорректные числовые значения — указать ошибку до сохранения. Обязательные измеренные величины должны быть положительными, счётчики — целыми неотрицательными; конкретные пределы выбираются после согласования полей. Неизвестное значение не превращается в ноль.
- Ошибка в уже сохранённом замере до публикации сметы — админ исправляет данные; прежнее значение остаётся в истории, фактическое сохранённое изменение порождает новое письмо. Исправление само по себе не сбрасывает заказ в более раннее состояние.
- Если новый результат замера меняет условия опубликованной сметы, админ отзывает ещё не согласованную версию по UC-09 или явно возвращает согласованную смету к подготовке по UC-09 и UC-10. Прежние замеры, состав и цена сохраняются в истории.
- Клиент успел отменить заказ или другой человек изменил данные — не сохранять результаты в закрытый заказ и не перезаписывать более свежие сведения без проверки.
- Повторная отправка без фактических изменений — без дубля помещений, события и email.

**Приёмка черновика:** клиент видит только свои измеренные данные по помещениям; сведения клиента и профессиональный замер различимы; запись даты не создаёт выполненный замер; первое сохранение переводит заказ к подготовке сметы; изменения сохраняют историю; для действия сохраняется одно задание на письмо; закрытый заказ не изменяется.

**Согласовано автором:** перечисленные поля и обязательность, показ клиенту сразу после сохранения без отдельной публикации и переход к подготовке сметы после сохранения выполненного замера.

**Согласованный повторный замер на этапе подготовки сметы:**

- Исправление значения при уже известных данных не требует нового выезда и не меняет состояние само по себе: на подготовке сметы заказ остаётся на подготовке сметы. Сохраняются событие истории и одно задание на письмо об изменениях.
- Если нужен фактический повторный выезд и подготовку сметы нельзя завершить, админ выполняет явное действие «Нужен повторный замер», при необходимости поясняет причину. Разрешён переход из подготовки сметы в ожидание замера в рамках того же активного заказа, без повторного принятия заявки.
- Дата повторного выезда согласуется и записывается по UC-06. Прежний визит и результаты не удаляются; в истории видно, почему заказ снова ожидает замера.
- После сохранения уточнённых результатов из ожидания замера заказ снова переходит к подготовке сметы. Не применять этот переход к любой правке на любой последующей стадии.
- Возврат — разрешённый переход с бизнес-причиной, а не свободный выбор любого прошлого статуса и не восстановление закрытого заказа.
- Изменение замеров само по себе сохраняет прежние условия опубликованной сметы. Новые условия отражаются в полной версии после отзыва или возврата к подготовке по UC-08–UC-10.

**Граница закрытого сценария:** UC-07 закрыт для этапа до проектирования, включая повторный выезд из подготовки сметы и возврат после уточнения результатов. Влияние изменений на уже опубликованную или подтверждённую смету рассматривается в UC-08/UC-09. Форматы числовых полей уточняются при проектировании замеров.

## UC-08. Подготовить и отправить смету — основной путь согласован

Согласованы состав полной сметы, внутренний черновик, отправка номерной версии и уведомление. Правила отзыва и пересмотра утверждены в UC-09. Вид исправлений в интерфейсе определяется при проектировании.

**Участник:** админ. **Условие:** заказ находится на подготовке сметы, есть актуальные результаты замера и достаточно договорённостей о работах.

**Цель:** сформировать понятное предложение по составу и стоимости и передать клиенту конкретную версию для согласования. Это не подтверждение отправленной заявки, а отдельное решение клиента о составе и цене заказа по UC-09.

**Согласованный состав сметы:**

- Одна или несколько позиций: название работы/материала, при необходимости помещение, единица измерения, количество, цена за единицу, вычисленная сумма.
- Количество обязательно и положительно; единица обязательна, например м², м, шт. Для работы с общей стоимостью можно использовать одну позицию «услуга», количество 1.
- Учебные цены задаёт админ, они не считаются реальными тарифами компании. Сервер проверяет значения и вычисляет сумму позиции и общий итог, не доверяя числам итога из браузера.
- Общий комментарий необязателен. Валюта проекта, точность и округление уточняются при проектировании. Скидки, налоги, предоплата и автоматический подбор всех позиций не входят в предложение автоматически.

**Полный состав версии.** Каждая версия сохраняет дату составления и содержит состав и итоговую цену всего заказа. Позиции, которые уже выполнены и входят в итог, оформляются так же, как остальные, без отметки и даты выполнения. Факты выполнения хранятся отдельно в заказе по UC-10. Изменение цены выполненной работы показывается клиенту и согласуется в составе новой версии. Исключённые позиции сохраняются в прежней версии. Сервер считает итог по позициям текущей версии, учитывая каждую работу один раз.

**Согласованный основной сценарий**

1. Админ открывает результаты замера и форму сметы. При необходимости сверяется с отдельными отметками о выполнении в заказе.
2. Добавляет позиции и цены, проверяет количество и общий итог. Площадь может подставляться из замера как исходное значение; окончательный состав формирует админ. Конкретная автоматизация не обязательна для первой версии.
3. При необходимости добавляет общий комментарий и сохраняет черновик. Можно закрыть страницу и продолжить редактирование сохранённых сведений позже; само сохранение черновика не отправляет его на согласование.
4. Закончив подготовку, выбирает отдельное действие «Отправить на согласование».
5. Сервер проверяет, что заказ не закрыт, находится на нужном этапе, использованные замеры и условия сметы актуальны и позиции заполнены корректно. Требования к неполным промежуточным данным при сохранении черновика нужно определить отдельно от проверки законченной отправляемой сметы.
6. Система сохраняет полную отправленную версию с датой составления, позициями, ценами, общим итогом, временем отправки и связью с использованными замерами. Отметки о выполнении остаются в заказе.
7. Заказ переходит из подготовки сметы к состоянию «Смета на согласовании».
8. Клиент видит отправленную смету в кабинете и получает одно информационное письмо о версии и новом статусе. В письме предлагается перейти к смете, но подтверждение выполняется отдельно по UC-09.

**Результат.** Клиент получает полное предложение по заказу для согласования. Во время пересмотра допустимый объём работ определяется по действующей утверждённой версии согласно UC-10. Переход обратно в выполняемый монтаж в системе происходит по UC-09 и UC-10.

**Согласованный сохраняемый черновик:** необходим для подготовки за несколько подходов. Не смешивать сохранение промежуточной работы с отправкой законченного предложения клиенту. Прежний вариант без сохраняемого черновика отклонён автором.

**Согласованная видимость:** черновик доступен только админу; клиент до первой отправки видит состояние «Подготовка сметы», но не промежуточные позиции и суммы. Сохранение внутреннего черновика не порождает email клиенту, отправка готовой версии — порождает. Это утверждённое уточнение/исключение из общего правила UC-15.

**Согласованная нумерация:** очередной номер клиентской версии назначается при отправке готовой сметы, а обычное сохранение черновика обновляет рабочий вариант без создания новой отправленной версии. Хранение промежуточной истории черновика и способ создания рабочего варианта из прежней версии уточняются отдельно.

**Граница UC-08.** Правила отзыва и пересмотра отправленной сметы согласованы в UC-09. Экраны сравнения и представление изменений выбираются при проектировании. При отправке клиенту должна быть явно видна изменённая цена выполненной работы.

**Другие крайние случаи:**

- Сведений недостаточно до первой отправки — согласованный возврат к ожиданию повторного замера по UC-07.
- Пустая смета, некорректные значения — ошибка до публикации; клиент не получает незавершённую версию.
- Если замеры изменили с другого устройства того же админа или из отдельной записи второго админа, устаревшая форма не отправляет смету. Админ проверяет актуальный замер.
- Клиент отменил заказ — публикация в закрытый заказ запрещена.
- Повторная отправка — без второй идентичной версии, повторного события и лишнего письма.
- Ошибка email — опубликованная смета остаётся в кабинете, доставка может повториться отдельно.

**Приёмка сценария:** сохранённый черновик можно открыть и продолжить после закрытия страницы, отдельно от отправки; клиент не видит его и не получает письма о его сохранении; серверный итог соответствует позициям; клиент видит только свою отправленную смету; отправка фиксирует новую номерную версию с датой составления и переводит к согласованию; история цен и исходных данных сохраняется; отдельная запись о выполнении не меняет отправленную смету и не требует повторного согласования; повтор не дублирует отправленную версию; закрытый заказ не изменяется. Отзыв и подтверждение выполняются по UC-09.

**Следующий шаг:** согласование актуальной версии и возврат на доработку в UC-09. Видимость черновика, отсутствие писем о его сохранении и нумерацию при отправке повторно согласовывать не нужно.

## UC-09. Согласовать смету — основной путь и конфликт действий согласованы

Согласованы подтверждение полной актуальной версии, отзыв, исходы конкурирующих действий и специальный возврат для пересмотра до или после начала монтажа. При пересмотре действует одна стадия заказа. Допустимые работы и фиксация выполнения описаны в UC-10, визиты в UC-06.

**Участники:** клиент, админ при переработке. **Условие:** свой активный заказ в состоянии «Смета на согласовании» с актуальной отправленной версией, не черновиком.

**Согласованный основной сценарий:**

1. Клиент открывает свою отправленную смету из кабинета или по ссылке из информационного письма. При отсутствии действующей сессии сначала входит обычным способом.
2. Изучает позиции, количества, цены, общий итог и комментарий.
3. Если согласен, нажимает «Подтвердить смету».
4. Сервер проверяет принадлежность заказа, его текущее состояние и то, что подтверждаемая версия всё ещё актуальна и не отозвана.
5. Система фиксирует клиента, время и конкретную версию с полным составом и итогом всего заказа. После утверждения она становится действующей. Прежнее согласование и версии выполнения остаются в истории. Устаревшая страница не может подтвердить другую версию.
6. Заказ переходит к ожиданию монтажа. Дата монтажа не назначается автоматически, работы не считаются начавшимися.
7. Клиент и админ видят результат. Подтверждение и смена стадии сохраняются одним действием с событием истории и одним заданием на email по UC-15.

**Результат:** однозначно определено согласованное предложение компании. Подтверждение фиксирует согласие со сметой. Онлайн-оплата и финансовый учёт в первый выпуск не входят.

**Вариант — клиент хочет изменения:** связывается с компанией вне сайта. Позиции и цены самостоятельно не редактирует. Сам факт разговора не меняет состояние и не отменяет смету автоматически; дальнейшее действие фиксирует админ. Отдельная кнопка отказа от конкретной версии пока не требуется в предложении: клиент может обсудить правки или отменить заказ до начала монтажа по UC-11.

**Согласованный явный отзыв до подтверждения:**

- Админ выбирает «Вернуть смету на подготовку»: текущая версия снимается с согласования, заказ возвращается к подготовке, факт отзыва и прежний вариант сохраняются в истории. Для клиента сохраняется одно задание на письмо о доработке. Старую версию подтвердить уже нельзя.
- Внутренний черновик готовится по UC-08 без показа и писем клиенту. Новая отправка создаёт следующую клиентскую версию, возвращает к согласованию и сопровождается письмом.
- Если требуется изменить замеры, сначала снять действующую отправленную смету с согласования. После возврата к подготовке возможны исправление сведений или повторный выезд по UC-07. Не оставлять старую версию доступной для подтверждения при пересмотре её исходных данных.
- Этот обычный отзыв относится только к ещё не подтверждённой версии. Уже сохранённое подтверждение не отменяется молча через то же действие. Для пересмотра подтверждённой сметы требуется отдельное осознанное действие возврата; оно доступно также после начала монтажа по принятому требованию, а правила продолжения работ определены в UC-10.

**Согласованные два исхода конфликта:**

1. Первым успешно сохранён отзыв админа либо замена актуальной отправленной версии: подтверждение клиента с прежней версией отклоняется как устаревшее. Нельзя незаметно подтвердить вместо неё новую.
2. Первым успешно сохранено подтверждение клиента: прежний запрос админа на изменение/отзыв до подтверждения отклоняется. Не применять его автоматически к новому состоянию. Админ должен заново увидеть результат и отдельно выполнить специальный возврат для пересмотра.

**Специальный возврат подтверждённой сметы:** заказ ожидает монтажа либо монтаж уже выполняется; прямое редактирование согласованной версии запрещено. Админ выполняет специальное действие пересмотра с возвратом к подготовке сметы (название кнопки уточняется при проектировании). Прежняя версия и факт её подтверждения сохраняются в истории. Возврат — отдельное изменение состояния с email, без молчаливой отмены прошлого решения. Затем действует обычная подготовка внутреннего черновика и отправка новой версии; прежнее подтверждение не распространяется на новый состав и сумму, нужно новое согласование. Возврат после начала монтажа входит в первую версию по требованию автора.

Факт прежнего начала работ не стирается; во время пересмотра бригада продолжает только согласованный объём по правилам UC-10. Вариант системного возвращения к монтажу описан в UC-10. Требование не открывает завершённые или отменённые заказы: их восстановление по-прежнему не предусмотрено.

**Монтажный визит при пересмотре.** Дата и интервал могут сохраниться, если весь объём визита и его цена по-прежнему покрыты действующей утверждённой сметой. Админ может согласовать с клиентом перенос для такого объёма и указать в карточке и письме, какие работы планируются. Визит, зависевший от новых условий, админ снимает и назначает заново после утверждения версии. Снять прежнее назначение можно без новой даты. Эти действия сохраняют стадию и историю согласований, а прежняя дата остаётся в истории по UC-06. Согласование новой версии возвращает заказ к ожиданию монтажа, переход к выполняемому монтажу фиксируется отдельно по UC-10.

**Техническое уточнение к слову «первым»:** запросы могут обрабатываться с перекрытием по времени. Побеждает допустимое изменение, первым зафиксированное под согласованной защитой состояния/версии, а не обязательно HTTP-запрос, раньше пришедший на сервер. Проверка актуальной версии/состояния и запись результата должны быть неделимы по отношению к конкурирующему действию. Одна лишь разница времени прихода или отдельная предварительная проверка этого не обеспечивают. Механизм защиты выбирается при проектировании базы и операций.

**Краевые случаи:**

- Клиент открыл старую страницу — отозванную/заменённую версию не подтверждаем, предлагаем актуальное состояние и при наличии новую версию.
- Клиент подтверждает во время действия админа — применяются два исхода выше. Проверять не только последовательные запросы, но и ситуацию, когда оба обработчика уже начали работу с одной старой версией. Не перезаписывать итог последним запросом.
- Заказ отменён — подтверждение запрещено.
- Повторное нажатие — без нового подтверждения, события и письма.
- Клиент долго не отвечает — само время не означает согласия, отмены или истечения сметы. Срок действия сметы отдельно не вводится этим черновиком.
- Письмо не пришло — актуальная версия и решение доступны в кабинете; ошибка доставки не отменяет сохранённое подтверждение.

**Приёмка сценария:** подтверждается только своя актуальная версия в допустимом состоянии; сохраняются состав, сумма, время и автор; успешное действие переводит к ожиданию монтажа и создаёт одно задание на письмо; старый вариант, закрытый заказ и повтор не создают лишних действий. При конфликте допускается только один совместимый результат, проигравший устаревший запрос не изменяет данные, историю и уведомления как будто он успешен. После подтверждения обычное редактирование запрещено; специальный возврат сохраняет прошлую версию и подтверждение, новая версия требует нового решения клиента.

Порядок возобновления и завершения согласован в UC-10. Утверждение версии фиксирует бизнес-согласие в учебном проекте. Юридическую силу для реального договора обсуждаем отдельно с учётом формы договора.

## UC-10. Начать, пересмотреть и завершить монтаж — основной путь согласован

**Участник.** Админ ведёт незакрытый заказ. Для системного начала, возобновления и завершения нужна актуальная утверждённая смета. Во время пересмотра физическое выполнение согласованного объёма и запись его фактов подчиняются правилам ниже.

**Сценарий:** отмечает начало монтажа в системе, после выполнения — завершение. При первом системном начале фактическая дата начала автоматически заполняется текущей датой; админ может отдельно уточнить её в параметрах заказа. Завершённый заказ сохраняется в истории и перестаёт занимать место активного.

**Принятое требование первой версии:** после начала монтажа админ может специальным действием вернуть незакрытый заказ к подготовке сметы. Основания могут включать изменение состава помещений, материалов или цены предложения. Изменение прайса не переписывает согласованную версию автоматически: новый состав/цена оформляются новой версией для клиента. Предложение запретить пересмотр после начала монтажа отклонено автором.

**Путь пересмотра после начала работ с согласованным разделением системы и фактов:**

1. Админ выбирает специальный возврат к подготовке сметы, при необходимости указывает пояснение. Фиксируются прежняя стадия, факт возврата и история. Клиент получает письмо.
2. У заказа одна стадия подготовки или согласования сметы. Фактически бригада продолжает только работы, объём и цена которых по-прежнему однозначно покрыты действующей утверждённой версией. Работы с новыми условиями или невыделенной общей ценой ждут утверждения. Например, первую комнату можно закончить по №1, если отказ от второй не меняет условий первой. При общей цене за две комнаты и отсутствии отдельной согласованной цены первой требуется новая смета.
3. Админ отдельно в заказе отмечает, какое помещение или какие работы в нём выполнены, когда и по какой утверждённой версии сметы. Эти отметки, замеры, прежние версии, согласования и первое начало сохраняются при возврате. Запись о выполнении сама по себе не меняет стадию заказа или отправленную смету и не требует повторного согласования.
4. Админ готовит полный черновик сметы по UC-08. Заметка может пояснить договорённость, а изменение объёма или цены оформляется новой версией. При необходимости уточняются замеры по UC-07. Если позицию исключили по согласованному изменению, прежняя позиция и факты работы остаются в истории.
5. Админ отправляет новую полную версию по UC-08, клиент согласует её по UC-09. Позиции выполненных работ, которые входят в итог, включаются в смету наравне с остальными. Их отметки о выполнении хранятся отдельно в заказе. Изменённая цена выполненной работы показывается клиенту для согласования. Визит сохраняется, переносится или снимается по UC-06.
6. После подтверждения заказ переходит в «Ожидается монтаж», затем действие админа «Возобновить монтаж» возвращает его в выполняемый монтаж. При первом начале используется «Начать монтаж». Это смена стадии в системе: физическая работа могла не прерываться. При возврате не перезаписывать уже заполненную фактическую дату первого начала; сохраняются событие перехода и одно задание на письмо. Явное возобновление согласовано, расположение и окончательная подпись кнопки определяются при проектировании.
7. После фактического выполнения админ завершает заказ обычным способом.

Согласованная цепочка: «Монтаж выполняется → Подготовка сметы → Смета на согласовании → Ожидается монтаж → Монтаж выполняется». Повторное ожидание отражает состояние процесса в приложении, а не отсутствие или обязательную остановку физической работы.

**Согласованная фактическая дата:** админ вправе исправить её в параметрах активного заказа, если автоматическое значение при первом системном начале не соответствует реальности. Исправление не меняет стадию и не переписывает события истории; сохраняются старое/новое значения и время действия админа, сохраняется одно задание на письмо по UC-15. При повторном входе в монтаж уже указанная дата не заменяется датой повторного перехода. Плановый визит, фактическая дата и время фиксации действия в системе — разные сведения. Окончательные типы полей и проверки дат определяются при проектировании.

**Следствие для прав:** возврат к подготовке и исправление фактической даты не отменяют факт того, что монтаж уже начинался. Правило самостоятельной отмены только до начала нельзя проверять одним лишь текущим статусом: после возврата отмена начатого заказа остаётся через админа.

**Согласованное завершение заказа:**

1. Заказ находится в состоянии «Монтаж выполняется», актуальная отправленная смета подтверждена, пересмотр не открыт.
2. По факту выполнения админ выбирает «Завершить заказ».
3. В форме завершения указывает фактическую дату окончания: по умолчанию сегодняшняя, можно исправить перед сохранением, если работы закончились раньше. Итоговый комментарий необязателен. Дополнительное подтверждение завершения клиентом не требуется: завершает админ.
4. Система проверяет актуальное состояние/версию и согласованность дат, не переписывая фактическое начало автоматически. Сохраняет фактическую дату окончания, отдельное системное событие и переводит заказ в «Завершён» одним действием.
5. Для клиента сохраняется одно задание на письмо о завершении. Заказ доступен в истории и освобождает место для нового активного заказа.

**Согласованные ограничения завершения:**

- При незавершённом пересмотре сметы завершать заказ нельзя, даже если физическая работа уже закончилась: сначала согласовать актуальную версию и отразить выполняемый монтаж в системе.
- Дата окончания не раньше фактического начала и не в будущем; при ошибке предложить исправить сведения до закрытия. Типы дат и часовой пояс уточнить при проектировании.
- После закрытия заказ не восстанавливается и его данные не редактируются обычными действиями активного заказа. Исправление даты окончания после закрытия этим сценарием не добавляется.
- Отдельная приёмка клиентом для завершения не требуется.
- Если другой человек успел вернуть заказ на подготовку, старый запрос завершения отклоняется; если завершение уже сохранено, возврат закрытого заказа не проходит. Проверка и запись защищаются совместно, как в UC-09. Повтор завершения не дублирует событие и письмо.
- Ошибка доставки email не отменяет завершение или сохранённую историю.

Указанные поля и условия завершения утверждены автором. Основной путь UC-10 закрыт для этапа до проектирования: первое начало, пересмотр, явное системное возобновление и завершение с фактическими датами. Точные типы и ограничения полей уточняются при проектировании.

До первого начала сохраняется обычное ожидание. В период пересмотра применяются правила допустимого объёма и цены работ и правила визитов по UC-06. Отмена начатого заказа описана в UC-11. Обязательность причины пересмотра и способ отображения фактов по отдельным позициям уточняются при проектировании.

**Далее:** UC-11 — отмена до первого начала и через админа после начала. Правила возобновления и завершения повторного утверждения не требуют.

## UC-11. Отменить активный заказ — согласован

**Уже согласовано:** клиент отменяет самостоятельно только до первого начала монтажа; после начала обращается к админу. Отмена сохраняет заказ в истории без восстановления и освобождает место для нового активного заказа. Текущий статус после возврата к подготовке не отменяет факт прежнего начала работ.

**Участники:** клиент, админ. **Условие:** заказ не завершён, не отклонён и не отменён.

**Согласованный путь клиента до начала:**

1. Клиент открывает свой активный заказ и выбирает «Отменить заказ».
2. Видит пояснение, что отмена окончательна; при желании указывает причину и подтверждает намерение. Причина необязательна.
3. Сервер проверяет владельца, актуальность состояния и отсутствие факта первого начала по данным/истории, а не только текущей стадии.
4. Заказ закрывается как отменённый; сохраняются инициатор, время, причина при наличии и история. Клиент получает одно информационное письмо.
5. Предыдущие замеры, сметы и назначения остаются в истории, но новые действия по выполнению/подтверждению закрытого заказа запрещены; клиент может создать новый.

**Согласованный путь через админа:**

- После первого начала клиент связывается с компанией вне сайта, обсуждает прекращение работ. Отдельный встроенный запрос отмены или чат не добавляется автоматически.
- Админ может отменить уже принятый активный заказ до начала или после начала, в том числе по инициативе компании. Для отказа от новой заявки/очереди по-прежнему применяется UC-05.
- При отмене админом причина обязательна и видна клиенту. В истории сохраняется исполнитель действия; необходимость отдельного поля для инициативы клиента/компании уточняется при проектировании и не подменяет обязательную причину.
- Отмена сохраняется в истории и создаёт одно задание на письмо. Клиент может создать новый заказ. Закрытый заказ восстановить нельзя.
- При начатых работах сохраняются фактическое начало, сведения о выполненных работах, их даты и ссылки на версии смет. Отмена не выдаётся за успешное завершение; дата отмены — отдельное событие. Оплата выполненного, компенсации и возвраты остаются за пределами сервиса.

**Краевые случаи и проверки:**

- Два запроса: отмена клиентом против начала монтажа — первым сохранена отмена, начало не проходит; первым сохранено начало, самостоятельная отмена не проходит, нужно обратиться к админу. Проверка и запись защищаются вместе.
- Заказ вернулся к подготовке сметы после начала — самостоятельной отмены у клиента всё равно нет. Поправка фактической даты не стирает факт начала.
- Клиент успел подтвердить смету — это само по себе не запрещает отмену, если первое начало ещё не было. Успевшая сохраниться отмена запрещает дальнейшее подтверждение/назначение/начало.
- Уже закрытый заказ или повтор запроса — не менять данные и не дублировать событие/письмо; завершённый заказ не превращается в отменённый.
- Назначенный визит после отмены не является действующим будущим заданием. Сведения о назначении сохраняются в истории; конкретное представление при проектировании расписания нужно согласовать.
- Неудача email не откатывает отмену.

**Приёмка сценария:** собственный активный заказ отменяется клиентом только до первого начала; после него действие выполняет админ; админ вправе отменить принятый активный заказ на любом этапе; его причина обязательна и видна клиенту, причина клиента необязательна; данные и факт выполненного сохраняются; закрытый заказ не возвращается; новый заказ разрешён; для отмены сохраняется одно задание на письмо.

**Граница:** основной UC-11 закрыт для этапа до проектирования. Полномочие админа и правила причин утверждены. Представление снятых будущих назначений уточняется при проектировании расписания. Далее — просмотр истории по UC-12.

## UC-12. Просмотреть историю — согласован

**Участники:** клиент или админ в пределах доступа. **Цель:** просмотреть прошлые договорённости и результат обращения без возврата закрытого заказа в работу.

**Принято:** завершённые, отклонённые и отменённые заказы сохраняются, восстановления и редактирования нет; клиент видит только свои записи, админ — заказы компании. Основной сценарий просмотра согласован автором; окончательная компоновка и сортировка уточняются при проектировании.

**Согласованный основной сценарий:**

1. Клиент открывает историю заказов в кабинете; она доступна и при наличии текущего активного заказа.
2. В списке видит номер, адрес, итоговое состояние и дату закрытия; предлагается сортировка от новых к старым.
3. Открывает заказ и просматривает имеющиеся замеры, отправленные версии смет и их согласования, историю визитов, отдельные записи о выполнении по помещениям с фактическими датами и ссылками на версии смет, заметки и причины закрытия.
4. История показывает прежние условия и факты выполнения. Итог всего заказа берётся из последней утверждённой полной сметы. Для каждой версии видны её дата составления, состав, цены и сохранённое согласование. При отсутствии замера или сметы это видно в карточке.
5. Новое обращение создаётся отдельным заказом, только если нет другого активного.

**Правила и крайние случаи:**

- История заказов — список закрытых обращений; история изменений внутри карточки — последовательность событий одного заказа. Это связанные, но разные представления, окончательный интерфейс выбирается позднее.
- Закрытый заказ доступен только для чтения: редактирование, согласование прежней сметы, начало/возобновление и восстановление недоступны. Отзыв — отдельное разрешённое действие после успешного завершения, не редактирование заказа.
- Внутренний черновик сметы клиенту не показывается и в архиве; он видит отправленные версии. Интерфейс версий по-прежнему отложен, а их сохранность не отменяется.
- Внутренние заметки ещё не определены: доступ к ним не открывается автоматически словом «история». Клиентская лента не должна показывать коды входа и технические данные доставки писем; конкретный состав событий уточняется при проектировании.
- Новый заказ не создаётся копированием старого и не заменяет его идентификатор; возможное заполнение формы из прошлого заказа отдельно не предлагалось.
- Нет закрытых заказов — пустая история; наличие активного заказа не скрывает предыдущие.
- Чужой идентификатор заказа не даёт доступа. Проверка владельца действует и в истории.
- Просмотр не меняет данные/состояние и не порождает email.

**Приёмка сценария:** доступны все свои закрытые заказы, имеющиеся данные сохранены, закрытый заказ не активируется и не редактируется, старые сметы не подтверждаются повторно, клиент не получает чужие/внутренние сведения; новый активный заказ не мешает просмотру прошлых.

**Граница:** UC-12 закрыт для этапа до проектирования. Согласован просмотр сохранённых сведений без восстановления, редактирования и повторения старого заказа. Представление истории уточняется при проектировании.

### Сквозная проверка UC-06 и UC-08–UC-12

Условные суммы в этом примере нужны для проверки правил, а не для расчёта реальных тарифов.

1. Клиент утверждает смету №1 на две комнаты. Первая стоит 100. Во второй отдельно оценены монтаж полотна за 60 и освещение за 40. Итог заказа по №1 составляет 200. Админ отмечает начало монтажа. 5 ноября бригада завершает первую комнату. Админ сохраняет отдельную запись в заказе о выполнении первой комнаты 5 ноября по смете №1.
2. Админ возвращает заказ к подготовке сметы для изменения освещения во второй комнате. В системе одна стадия. При подготовке и согласовании новой версии бригада может выполнить монтаж полотна за 60, если его объём и цена остались прежними и однозначно следуют из №1. Освещение на новых условиях ждёт утверждения. Если бы цена второй комнаты была общей, а цену монтажа полотна отдельно нельзя было определить, этот монтаж также ждал бы новой сметы.
3. Если прежний визит назначен только для согласованного монтажа полотна, админ может сохранить его или согласовать перенос, например на 7 ноября с 14:00 до 16:00. В карточке и письме указаны монтаж полотна во второй комнате, дата и интервал. Если визит зависел от изменения освещения, админ снимает его, клиент видит отсутствие назначения и получает письмо. Прежняя дата сохраняется в истории. В обеих ветвях стадия и согласования сохраняются.
4. Админ составляет и отправляет смету №2 6 ноября, клиент утверждает её 8 ноября. В смете указаны дата составления и позиции всего заказа. Первая комната стоит 100, монтаж полотна во второй — 60, новое освещение — 70. Итог №2 составляет **230 = 100 + 60 + 70**. Первая комната учтена один раз, прежние 40 за освещение остаются в истории №1. Выполнение первой комнаты 5 ноября по №1 видно в отдельной записи заказа. Если в ветке переноса полотно установили 7 ноября, админ добавляет отдельную отметку о монтаже полотна во второй комнате по №1. Эта запись не меняет отправленную смету №2 и не требует повторного согласования.
5. После утверждения №2 заказ ожидает монтажа. В ветке снятия админ согласует и записывает новую дату для работ по №2. В ветке переноса визит 7 ноября остаётся в истории. Для оставшихся работ при необходимости согласуют новый визит по №2. Админ явно возобновляет монтаж в системе без перезаписи первого начала, фиксирует оставшиеся выполненные работы по применимой утверждённой версии и завершает заказ.
6. В истории закрытого заказа видны обе сметы, их согласования, факты выполнения с датами и версиями, перенос либо снятие визита и завершение. Действующий итог всего заказа берётся из №2 и составляет 230. При отмене вместо завершения UC-11 сохраняет эти же сведения и фиксирует отмену как отдельный исход.

## UC-13. Оставить отзыв — отложено, основные правила согласованы

Выпуск с отзывами также добавляет фотографии заказов и отзывов, отдельный сервис файлов и S3-совместимое хранилище. Места загрузки фотографий в заказе и правила доступа уточняются при проектировании этого выпуска.

**Участник:** клиент. **Уже принято:** один отзыв на свой успешно завершённый заказ, обязательная оценка 1–5, необязательные текст и фото, немедленная публикация без проверки админом и уведомление админу о новом отзыве. Отзыв не делает заказ активным. Владелец может редактировать и удалять отзыв. О новом отзыве админ получает письмо на служебный email.

**Согласованный состав:** обязательная целая оценка от 1 до 5, необязательные текст и фотографии. Для каждого своего успешно завершённого заказа клиент может в любое время оставить один действующий отзыв. После удаления прежнего отзыва можно написать новый на тот же заказ.

**Согласованный основной путь с деталями для проектирования:**

1. Клиент открывает завершённый заказ в истории и выбирает «Оставить отзыв».
2. Указывает оценку, при желании текст и фотографии именно для отзыва.
3. Видит пояснение, что отзыв публикуется сразу без предварительного одобрения.
4. Отправляет отзыв. Сервер проверяет владельца, успешное завершение заказа, корректность полей и отсутствие другого отзыва на этот заказ.
5. Система сохраняет отзыв с привязкой к конкретному заказу и автору. Клиент видит результат в своём кабинете; сам закрытый заказ не меняет состояние.
6. Отзыв сразу становится публичным, админу отправляется уведомление. Доставка/прочтение сообщения не являются условием публикации. Админ получает письмо на настроенный служебный адрес с оценкой и ссылкой на отзыв в панели.

**Предлагаемые правила и крайние случаи:**

- Отменённый или отклонённый заказ не даёт права на отзыв по этому сценарию, даже если при отмене частично были выполнены работы. Иная обратная связь потребует отдельного решения.
- Другой активный заказ не препятствует отзыву по ранее завершённому.
- Повторная отправка/две вкладки не создают два отзыва на один заказ.
- Закрытые фото заказа не становятся публичными автоматически: в отзыв включаются отдельно выбранные автором вложения с явным объяснением публикации. Конкретный механизм добавления фото уточняется при проектировании.
- Для публичной части не раскрываются адрес объекта, email, телефон, номер заказа и внутренние документы. Публичное имя автора и набор видимых полей ещё нужно определить.
- Ошибка загрузки фото не должна выдавать отсутствующий файл за сохранённый. Допустимость отправки без проблемного фото, число файлов, типы и размеры определяются отдельно.
- Отзыв — отдельная запись; его отправка/изменение не редактирует замеры, сметы, даты или итог заказа.

**Редактирование и удаление.** Автор может менять оценку, текст и фото. Правки сразу видны на сайте, хранится текущая редакция. Автор и админ могут окончательно удалить опубликованный отзыв. Он виден на сайте до удаления автором или админом. После удаления автор может оставить новый отзыв на тот же заказ.

Публичное имя, обязательность причины удаления админом и уведомление автора при таком удалении остаются открытыми решениями.

**Приёмка основного пути:** только владелец успешно завершённого заказа отправляет отзыв с оценкой 1–5 и необязательными текстом/фото; один заказ не получает дублей; отзыв сразу публикуется без проверки, админ получает уведомление; связь с заказом сохраняется; закрытые материалы/контакты не раскрываются; заказ не возобновляется. Владелец может отредактировать отзыв или окончательно удалить его и написать новый на тот же заказ. Админ также может удалить отзыв. Действующий отзыв виден до удаления автором или админом. Срок давности заказа и наличие другого активного заказа не препятствуют отзыву. Служебное письмо формируется только при новой публикации, в том числе после удаления прежнего отзыва и создания нового.

Основные правила UC-13 согласованы. Публичное имя уточняется при проектировании представления отзыва. Правила email админу определены в UC-15.

## UC-15. Получить email об изменении заказа — основной порядок согласован

**Получатель:** клиент, на подтверждённый email его учётной записи. **Инициатор:** система после сохранения соответствующего действия клиента или админа.

После выпуска отзывов по UC-13 предусмотрено письмо админу на служебный email с оценкой и ссылкой на отзыв в панели. Письмо формируется при новой публикации, включая новый отзыв после удаления предыдущего. Публикация происходит сразу после сохранения.

**Согласованный охват:** создание заявки и каждое сохранённое изменение её статуса или информации заказа, независимо от того, выполнил его админ или клиент. Это общее правило для всех сценариев, а не закрытый перечень избранных этапов. Оно распространяется на принятие, очередь, отказ, даты и интервалы визитов, снятие даты, замеры, сметы, сведения заказа, заметки, начало и завершение работ и отмену при появлении соответствующих действий.

**Дополнительного подтверждения заявки нет:** после успешной отправки формы заказ сразу создан. Письмо о создании — информационное, без запроса подтвердить заказ, ссылки активации или ожидания ответа. Оно не влияет на возможность обработки админом. Код подтверждения email до заполнения формы и предусмотренное отдельным сценарием согласование сметы этим решением не отменяются.

**Одно уведомление на действие.** Для сохранённого изменения, подлежащего уведомлению, создаётся одно сохранённое задание на письмо. В нём перечисляются изменения этого действия. Повторы доставки при сбое используют то же задание. Повторное сохранение прежних значений и технические обновления доставки не создают задания. Внутренний черновик сметы остаётся исключением, а отправка номерной версии создаёт задание. Границы уведомлений о других непубличных материалах уточняются.

**Согласованный сценарий доставки**

1. Действие фиксируется в истории. Если оно подлежит уведомлению, по его событию создаётся одно задание на письмо.
2. При создании заявки `OrderService` одной транзакцией сохраняет заказ, событие истории и запись для публикации. Отдельный процесс публикации в составе `OrderService` читает запись из базы и передаёт событие через RabbitMQ сервису уведомлений. Пока брокер недоступен, запись ждёт публикации, а сохранённая заявка доступна клиенту и админу. После восстановления публикация продолжается. Сервис уведомлений сохраняет одно задание по идентификатору события и отправляет письмо на подтверждённый email из события. Повторная доставка использует то же задание.
3. Письмо содержит номер заказа, краткое описание изменения на момент события и ссылку на карточку. Для открытия карточки действуют обычные правила входа.
4. Письмо об отказе включает причину, письмо об очереди — пояснение или стандартный текст. Письмо о переносе монтажа включает новую дату, интервал и работы визита. При снятии письмо сообщает, что назначение снято и новая дата пока не согласована. Точные шаблоны уточняются при проектировании.
5. Клиент открывает кабинет и видит фактическое актуальное состояние, даже если после формирования письма уже были другие изменения.

**Согласованные повторы.** Изменение заказа сохраняется независимо от отправки письма. При временном сбое система повторяет доставку того же уведомления. Если попытки исчерпаны, фиксирует ошибку отправки. Повтор исходного действия использует существующее событие. Количество попыток, интервалы и механизм обработки выбираются при проектировании.

**Границы:** публикация новой сметы, изменения монтажа, завершение и отмена теперь охвачены общим правилом, согласовывать сам факт email для этих изменений повторно не требуется. Содержание шаблонов уточняется при проектировании. Письма админу о новых заказах отдельно не согласованы. Автоматические напоминания за заданное время до визита не входят в это решение.

**Приёмка.** Создание заявки и согласованные изменения имеют сохранённое событие и одно задание на письмо. При сбое повторяется доставка того же задания. Письмо о создании информационное. Перенос и снятие передают клиенту актуальную договорённость либо её отсутствие на момент события. Повтор действия не дублирует заказ, событие или задание.

## UC-16. Разослать сообщение о внеплановой ситуации — отложено

Админ сможет оповестить затронутых клиентов одним действием, например при аварии или массовом переносе визитов. Для будущего сценария предложена отправка независимо от событий отдельных заказов.

Предложение для будущего сценария — админ выбирает затронутые заказы, проверяет список получателей и отправляет сообщение. Для каждого получателя формируется собственное задание на доставку с отдельным результатом и повтором при временном сбое. Связь рассылки с пакетным изменением дат визитов и границы выпуска уточняются отдельно.

## Исключённый сценарий

UC-14 «Удалить заброшенную заявку и освободить email» отменён новым порядком подтверждения до заказа. Неподтверждённых заказов и постоянных неподтверждённых учётных записей больше нет. Очистка временных запросов кодов — техническая задача будущего проектирования, без отдельного действия админа над заказом.
