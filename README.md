# Ceilings

Учебный веб-сервис компании по замеру и монтажу натяжных потолков в России. Первая версия включает кабинет клиента и панель админа.

Актуально на 24 ноября 2026 года. Собраны локальный Compose и вход клиента и админа по email-коду. [Инструкция локального Compose](docs/local-compose.md) · [Проверка основы](docs/local-compose-report.md) · [Проверка входа](docs/login-report.md)

В первой версии клиент открывает страницу личного кабинета напрямую. Компания ведёт заказы в отдельной панели админа. Без сессии на странице кабинета сначала доступны только поле email и кнопка «Получить код». В той же форме появляется поле кода. По правильному коду открывается существующая учётная запись или создаётся новая. Сессия действует 30 дней на устройстве. Если заявок ещё не было, сразу открывается первая форма. При активном заказе открывается он, а если все заказы закрыты, доступны история и кнопка «Оставить заявку». Для первой и повторной заявки нужны подтверждённый email, имя, российский телефон с `+7` или `8` и полный адрес объекта одним полем, без отдельного выбора города.

## Ключевые правила

Замер бесплатный. Оплаты, задолженность и возвраты компания ведёт вне сервиса. Онлайн-оплата и финансовый учёт исключены из первого выпуска. Автор склоняется исключить их из Ceilings целиком, окончательное решение ждёт подтверждения.

Первую персональную запись с ролью «Админ» создаёт человек, который разворачивает приложение. Служебную команду запускают после настройки базы и до приёма заявок. Один админ может работать с нескольких устройств. Если понадобится второй сотрудник, ему выдают отдельную запись с той же ролью. История фиксирует автора действия, а доступ отзывают у конкретного человека. Клиентский вход не выдаёт прав админа.

Основной путь заказа, история и уведомления описаны в [юз-кейсах](docs/use-cases.md). Каждая версия сметы содержит полный состав и цену заказа и дату составления. Отметки о выполнении хранятся отдельно в заказе с указанием помещения, фактической даты и версии сметы. При пересмотре стадия заказа одна, бригада продолжает только работы с объёмом и ценой, покрытыми действующей утверждённой сметой.

Админ может сохранить или перенести визит для согласованного объёма. При переносе клиент видит работы визита в карточке и письме. Назначение по пересматриваемым условиям снимается с сохранением истории, новую дату согласуют после утверждения сметы. Перенос и снятие сохраняют стадию и историю согласований.

После первого выпуска запланированы лендинг, отзывы, предварительный калькулятор, антифрод и массовая рассылка. Фотографии заказов и отзывов появятся в выпуске с отзывами вместе с отдельным сервисом файлов и S3-совместимым хранилищем. Ограничения на запросы и попытки ввода email-кода входят в первый выпуск.

Стек Ceilings — FastAPI, SQLAlchemy, PostgreSQL и Docker. Веб-приложение, сервис доступа, `OrderService` и сервис уведомлений работают отдельно. У трёх сервисов с данными по собственному экземпляру PostgreSQL. Заказ, событие истории и запись для публикации сохраняются одной транзакцией. Отдельный процесс публикации в составе `OrderService` передаёт сохранённые события брокеру (transactional outbox). Информационное письмо отправляется после доставки события через брокер. Брокер первого сценария — RabbitMQ. Web API вызывает `OrderService` и `AuthService` через Envoy-sidecar по mTLS. В каждом из трёх сервисов приложение и его Envoy соединяются через свой Unix-сокет в отдельном томе. Приложения подключаются к своим БД по отдельным соединениям.

Сервисы подключаются к PostgreSQL и RabbitMQ напрямую по TLS с проверкой сертификата и имени сервера. Порты остаются во внутренних сетях Compose. Базы и брокер ограничивают доступ по отдельным учётным записям и правам. [Схема подключений и прав](docs/first-scenario-design.md#подключения-к-postgresql-и-rabbitmq)

В локальном Compose Web открывается по `https://app.ceilings.test:8443`, интерфейс тестовой почты Mailpit — по `https://mailpit.ceilings.test:8443`. Оба адреса обслуживает Envoy Web на loopback. Для доверия браузера используем локальный CA от `mkcert`. [Схема локального HTTPS](docs/first-scenario-design.md#локальный-https-для-браузера)

Для клиентов и админов согласованы JWT access tokens сроком до 5 минут, refresh tokens со строгой ротацией и серверные сессии в `AuthService`. Web API локально проверяет JWT. После отзыва сессии клиентское чтение своих заказов по ранее выданному токену возможно до его истечения. Подача заявки и каждый защищённый запрос админа, включая чтение, требуют актуальной проверки сессии и прав. `OrderService` проверяет принадлежность заказа вместе с чтением по доверенному ID пользователя. Каждый refresh token можно обменять один раз. Повторное предъявление использованного токена отзывает связанную сессию. [Политика ротации и хранения токенов](docs/first-scenario-design.md#хранение-и-ротация-токенов)

Для реальной SMTP-доставки согласованы TLS с проверкой сервера и учётные данные провайдера. Локальный Mailpit настраивается отдельно, автоматического перехода на незащищённую отправку в реальном режиме нет. Для внутренних сертификатов выбран `step-ca`; причины и альтернативы описаны в решении 004 [журнала решений](docs/decisions.md). Первую выдачу сертификата разрешает оператор развёртывания одноразовым токеном для конкретного имени и запроса. Ключи Envoy хранятся в отдельных файловых каталогах вне репозитория. Зашифрованную резервную копию CA храним на внешнем диске. Детали публикации и отзыва сертификатов описываются в техническом дизайне.
